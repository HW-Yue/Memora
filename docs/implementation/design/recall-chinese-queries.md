# 中文与短词的召回：为什么「实习经历」搜不到

状态：**已实现并合回主线**（2026-09-21）。用户在 Admin 搜索页实测发现的问题。

## 实测（`me` 库，关键词臂）

| 查询 | 结果 |
|---|---|
| `oppo` | 命中 4 条（正文里有 "OPPO"） |
| `实习` / `经历` / `后端` | **被拒绝**：`RECALL needs at least 3 characters` |
| `实习经历` | **空** |
| `实习 经历` | **空** |
| `实习经历`（向量臂） | 命中：`实习/OPPO`、`实习/悠悠有品` 等 |

## 病因（两层，都不是"没做切分"这么简单）

1. **索引是 trigram（连续子串）**：FTS5 的 trigram 分词器把正文切成 3 字滑窗，所以
   - **1–2 个字符的查询永远匹配不到任何东西**——这就是那条"至少 3 个字符"的拒绝存在的原因：
     空结果读起来就是"没找到"，宁可拒绝；
   - 更长的查询被当成**一整段连续子串**：`实习经历` 要求正文里真的连着出现这四个字，而没有任何
     正文（每行只索引 `title` + `summary`）是这样的——语义树节点叫 `实习`、表描述写
     "实习与工作经历"，**树节点名与表描述都不在被索引的正文里**。
2. **查询端不切分**：中文没有空格，`实习经历` 就是一个词，引擎不会把它拆成 `实习` + `经历`。

用户猜的两条里，**"向量没做好"其实是他跑着的 Admin 是旧 bundle**（前端编在二进制里，没接上
向量支路），重启后同一个问句走向量臂是能答的；**"没做切分"是真的**。

## 顾问的结论（2026-09-21）

- **只降阈值 + 短词走扫描，修不好他举的那个 bug**：`实习经历` 是 4 个字符、每个词都 ≥3，
  按"最短词选路径"的规则仍然走倒排，仍然返回空。
- 真正的病因是两条：**索引面太窄**（树节点名、表描述不进正文）+ **中文没切分**。
- 最大风险：**修法与病因错配**，制造"已修复"的假象。
- 次生风险：`LIKE` 扫描没有相关性信号、只能按 `unit_no` 排序，喂给 RRF 相当于**注入一条伪排名臂**，
  会稀释向量臂的真信号。

## 实测：病因在索引侧，不在排名（临时 SQLite，未碰实例）

同一句话，一次连着写、一次把词用空格隔开：

| tokenizer | `实习`(2) | `经历`(2) | `后端开发`(4 连续) | `后端开发实习`(6) |
|---|---|---|---|---|
| trigram | MATCH **0** / LIKE 2 | MATCH **0** / LIKE 1 | MATCH 1 | MATCH 1 |
| unicode61 | MATCH 1（只有被空格隔开的那条） | MATCH 1 | MATCH **0** | MATCH **0** |

`bm25()` 是**排名函数**：真实命中时正常排序，`MATCH` 为 0 时没有东西可排（两条都实测过）。
所以"bm25 应该能查两字词"是把 analyzer 与 similarity 混在一起——ES 里同样要靠 `ik`/`jieba`
或 `ngram(min_gram:2)`，换 similarity 无用。

## 方案（已实现 2026-09-21，分支 `feature/cjk-bigram-recall`）

1. **索引换成二字滑窗**：每个单元的载荷切成**相邻两字对**作为 token（标点断行；ASCII 与中文
   同样按字符对切；单字成一段时保留该字），写进派生 FTS，`tokenize='unicode61'` 只负责按空格
   分词。两字词就是一个 token，天然可索引；`实习经历` → `实习 习经 经历`。
   **写端与读端共用同一个函数** `recallTokens`（`internal/sqlstore/recall_tokens.go`）：
   两边各切一次必然漂移，而漂移的后果是静默零召回。
2. **查询按「命中越多排越前」匹配，不做全中（AND）**：查询的词对用 `OR` 连接，BM25 按命中词数
   排序。**这是与顾问建议（AND，空结果再降级）不同的一处**，理由记在 `docs/decisions.md`：
   AND 会把"只写了实习"的行排除掉，正是用户说的"搜不到"；OR + BM25 保证"分享了查询里某个词的
   行一定在结果里，只是排在后面"。
3. **不加 `instr()` 连续性后置过滤**：契约规定召回只给位置、名次由融合读；再叠一层"必须包含原串"
   的过滤等于把 OR 又变回精确串匹配，与上一条冲突。连续性由 BM25 的命中词数自然体现。
4. **最低长度 3 → 2**（用户要求）；1 个字符拒绝——它连一个 token 都凑不出，却几乎出现在每一行，
   返回列表就是整库按行号排。
5. **trigram 不留**：两套索引＝双份膨胀 + 两条分叉逻辑。
6. **迁移按文件版本做**：FTS 是派生层——drop 旧虚拟表 → 按同一条 DDL 建新表 → 用 `recallTokens`
   重建 `payload_index` 与索引行，全程一个事务；同时 **`PRAGMA user_version` 1 → 2**
   （旧二进制只会继续按 trigram 建表并静默零召回，必须被版本挡住）。载荷、`content_hash`、
   向量全不动，**不需要重嵌**。
7. **Admin 搜索框最低 2 个字符**，前端文案同步。

## FTS5 现在负责什么（2026-09-25 复查）

切分归我们，FTS5 只承担「词 → 候选集 → 排名」这一段：

- **我们**：`foldRecallText`（全角→半角）+ `recallTokens`（相邻二字对）。索引列存的是切好的
  空格 token 串，不是正文；写端与读端调的是同一个函数。
- **FTS5**：倒排表本体（term → doclist 与位置）、term 并集求值、`bm25()`、与行写入同事务的索引
  维护、外部内容（不存第二份正文）。`unicode61` 在这里只剩两件事：**按空格切**、**折大小写与
  音标**——`foldRecallText` 没有 ToLower，所以"大小写不敏感"是 FTS5 给的，不是我们做的。
- **查询**：同一个函数切查询串，每个 token 加引号（查询是内容，不是 FTS5 语法），用 `OR` 连接。

实测（临时 SQLite，5000 units，未碰实例）：`EXPLAIN QUERY PLAN` 是
`SCAN f VIRTUAL TABLE INDEX 0:M1` + `SEARCH u USING INTEGER PRIMARY KEY (rowid=?)`，即真的走
倒排索引；`fts5vocab` 里 `实习` 是**一个 term**。代价：中文相邻字对天生高频，`ORDER BY bm25(...)`
拿不到有序索引，命中的行都要进临时 B 树排序，`LIMIT` 不能提前收工——成本随 doclist 长度走，
不随表大小。磁盘：表 0.39 → 0.71 MB（多出物化的 token 流），索引 0.22 MB，合计 0.93 MB
（同语料下 trigram 0.66、unicode61 0.52）。

## 验收（已固化为测试）

- `internal/sqlstore/recall_cjk_test.go`：`实习`/`后端`/`开发`/`端开` 命中、`oppo`/`OPPO`/`opp`、
  `实习经历` 找到"只写了实习"的行且整串那段排第一、命中越多越靠前、`"OR"`/`C++` 这类查询当内容
  而不是 FTS5 语法、1 字拒绝 2 字通过、旧文件（trigram + `user_version=1`）重开后重建并置为 2、
  `user_version=99` 的文件拒绝打开。
- 红-绿证据：把 `recallTokens` 换回按空格切并关掉迁移分支，六条新用例全红（已实测）。
- `./scripts/ci.sh` 全绿；`internal/adminui` 的冻结 bundle 随前端文案一起重刷。
- **已知代价（不是 bug）**：查询里任意一个词对命中了活着的正文，那一行就会被召回，哪怕原串已经
  不在了。`recall_keyword_test.go` 里两条"旧文本召不回"的用例因此改用**不与新正文共享词对**的查询
  ——它们现在测的是"索引跟着编辑走"，而不是"任何带公共字的查询都空手而归"。

## 为什么不用 jieba（顾问 2026-09-21 结论）

**结论：现在用 bigram，词典分词留作日后可替换的切分实现。**

- 这个语料正是词典最吃亏的地方：**个人库 + 大量 OOV 专有/自造词**（`悠悠有品`/`CoHabitat`/
  `DSH`/`原醛`）。jieba 对未登录词只能靠 HMM 猜或扩词典，而这些恰恰是最需要查准的词；
  **bigram 对专名零漏召**。
- 规模站在 bigram 这边：几千行的倒排表，bigram 那点 token 膨胀无关痛痒；当时还打算叠加一层
  `instr()` 连续性后置过滤（跑在几十条候选上等于免费，过滤后的 bm25 是**真排名**），**但最终
  没有采用**——它会把放宽的 OR 又变回精确串匹配，见「方案」第 3 条与 `docs/decisions.md`
  （2026-09-21）。
- ASCII 词不受影响，但也不是"按 unicode61 的规则切"：它和中文一样按**字符对**切
  （`backend` → `ba ac ck ke en nd`），所以英文同样是子串可召回；`unicode61` 在这里只负责
  按空格切与折大小写。
- 共同约束那条更关键：切分读写共用、**词典版本一升就要全量重建索引**。bigram 的切分是纯函数、
  零版本、零依赖，确定性可以直接被测试钉死；词典方案把检索质量绑上一个**会漂移的数据文件**，
  OOV 一出现就要扩词典再重建——没必要把重建触发器从"代码变更"扩大到"数据变更"。

**弃选**：`gojieba`（cgo）——为它引入 C++ 工具链，与"3 个直接依赖、一条命令编双架构"的发行路径
不值当；`jiebago`/`sego`（纯 Go）可行，但词典进仓库是几 MB 膨胀，换来的只是中文散文那一层的
切分优雅——而散文恰恰是**向量臂已经覆盖**的部分。

**什么时候再换**（切换判据，写死在这里）：bigram 的精度真正成为瓶颈时——正文上万行、误召可测量。
切分函数集中在一处，"bigram → 词典分词 + 重建一次索引"的替换成本本来就低。

## 上一版方案的验收（**已被取代**，2026-09-25 标注）

这一节是上一版方案（带 `instr()` 连续性后置过滤）的验收标准。其中一条与现行实现**相反**：
「只含 `实习` 与 `经历` 但不相邻的文档**不得**因它命中」——最终方案去掉了那层过滤，所以这类文档
**会**命中，只是排在后面。**不要照这一节验收。**

现行标准见上面「验收（已固化为测试）」；为什么去掉过滤见「方案」第 3 条与 `docs/decisions.md`
（2026-09-21）。这一节留在这里只为追溯上一版方案。
