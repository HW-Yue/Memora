# 灾难恢复链

状态:**已验通**(2026-09-13,`988ab7e`)。
[记录文件的索引与权威](./record-index-and-authority-v1.md)§6 那道硬门的实现
与结论。代码在 `internal/disasterrecovery`。

编写原则同[存储层总览](./README.md):每条断言都能指到具体文件与测试。

## 1. 链是什么

两半,缺一不可:

- **全量**:记录日志的**字节前缀**,拷到 `<backup>/base.memora`;
- **增量**:`internal/binlog`,每笔提交一帧,保留期 30 天。

接起来的是一个 **binlog 坐标**(`binlog.Position`:第几个段、段内多少字节),
和全量一起写进 `<backup>/base.json`。恢复 = 把前缀拷回去 + 从坐标回放日志。

**页文件不备份、不恢复。** 它们是导出来的:恢复完开库就会重建。这正是这条链
能当底的原因——它备的不是同一份东西的第二个副本。

## 2. 为什么全量是字节前缀,而不是逻辑快照

计划原先写的是 `nativesnapshot.Export`／`Import`,理由是「已有」。跑完端到端
发现两半接不上:

| | 逻辑快照 | binlog |
|---|---|---|
| 变更序号 | 导入时从 1 重新分配 | 当时真正写下的号 |
| 目录对象 | 只留当前版本 | 带版本链上的每一环 |
| 记录 ID | 由重放过程自己算 | 原样带着 |

一个 4 次写的库,导入后基底停在变更 2,日志从 5 续,中间 3、4(两笔 DDL)
不存在。`changeindex` 的 `Bootstrap`(`store/changeindex/index.go:107`)要求
序号从 1 起连续,直接拒绝。**这是两种格式的性质,不是能修的 bug**,所以钉成
`TestALogicalSnapshotIsNotARollforwardBase` 而不是去补。

逻辑快照仍然是迁移与跨引擎比对的正确工具(它的哈希只跟「库是什么意思」有关,
两个引擎装同样的数据必须哈希相同),**只是不能当前滚的基底**。

字节前缀的性质正好相反,也正是这里要的:记录日志只追加,**提交边界以下的字节
此后不再变**。所以备份可以在库开着、还在写的时候直接取,并发写只是在写被拷
的那一段之后。不用停库,不用加锁。

## 3. 取备份的顺序只有一种是安全的

`Backup` **先读 binlog 位置,后读记录日志长度**。

中间提交的事务会同时落在两边:它在拷贝长度以下,也在回放起点之后。
**重叠可恢复**——恢复时整笔跳过,而且要逐字节比对过才算「已有」。
反过来(先读长度、后读位置)则是一个空洞:那笔事务两边都没有,
恢复出来的库中间少一笔提交,**之后没有任何检查会发现**。

跳过是整笔的,不是逐条:记录日志一笔事务的记录是一起发布的,
只有一部分在基底里不是重叠,是损坏,报 `ErrDiverged`。
同一个记录 ID 带着不同的字节也是 `ErrDiverged`——那是两个不同的库。

## 4. 够不着就报,不半恢复

备份比日志保留期还老时,中间的事务已经没了。把剩下的段接着放会造出一个
中间缺一段的库,**比没恢复更糟**,所以 `ReplayFrom` 报 `binlog.ErrGap`。

`Restore` 中途失败会删掉已经写出的记录日志。留着的话,操作员手上会有一个
能打开、能读、缺了备份之后全部内容的库——最值得避免的那种失败。

## 5. 恢复出来的库是新的备份世系

恢复**不往 binlog 里回写**。往正在回放的日志里追加会把历史写第二遍。
所以恢复完要**先取一次新全量**再依赖它。这一条写在 `Restore` 的注释里。

## 6. 转正之后

形状不变,换的是全量那一半拷什么:今天拷记录日志的前缀,记录文件退出正确性
路径之后拷页文件。这正是 InnoDB 物理备份 + binlog 的形状。
