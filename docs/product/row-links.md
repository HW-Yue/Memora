# 数据行之间的双向链接

状态：**方向性结论**（2026-09-13）。
分层前提见 [ADR-0011](../decisions/0011-pure-storage-engine-tables-everything.md)；
链接遇到废弃行的处理见 [数据行的生命周期](./row-lifecycle-successor.md)。

## 一句话

链接是数据行上的一个字段：写明链到哪一行，并带上那一行的摘要。
不单独建关系表，也不是独立的对象。

## 字段

数据表的每一行带一个默认字段 `links`（与 `route_leaf_id` 同类，先存为 TEXT 里的 JSON）：

```text
links: [
  { row_id: 对方行的 RowID, summary: 对方行的摘要, revision: 摘要取自对方哪个 revision },
  ...
]
```

RowID 全局唯一，但**唯一不等于可定位**：调用方拿到一个 row_id 后得知道去哪张表点查，
倒推对面那一面也要有落点。所以链接条目**持久化对方的表**（`table` 与 `table_id`）——
这是规格原来那句话说漏的地方（2026-09-21 修订，顾问指出）。

## 双向

A 链到 B 时，**一个事务内**同时写两面：

- A 的 `links` 加 `{ B, B 的摘要 }`；
- B 的 `links` 加 `{ A, A 的摘要 }`。

删除链接同样两面一起删。任何时候两面必须一致，不允许只有一面。

读一行时，`links` 里的摘要让 Agent 不回表就知道对面是什么；
要事实仍按 `row_id` 点查对方行。

## 与废弃行

对方行被拆分或合并后，链接按[生命周期](./row-lifecycle-successor.md)懒更新：
改指全部接替者，两面一起改，每个接替者的摘要取自接替者本身。

## 与删除

**删除不走懒更新。** 行被[归档式删除](./row-delete-archive.md)时，同一个事务里把对面
那一面摘掉：链接两面都存，被删行自己的 `links` 就是「谁指向我」的清单，逐个到对面行里
删掉这一条，对面行照常 `revision + 1` 并写 history。删除成功后不留悬空链接。

## 写入与读取（已实现）

写入走**完整快照** option，与 `route_leaf_ids` 同构：

```json
{"mutation": {"links": [{"row_id": "row_x"}, {"row_id": "row_y", "table": "other"}]}}
```

- **`nil` 不动、`[]` 清空**（与挂载快照同一条区分）；
- 只写 `row_id` 时先在**本表**解析；本表找不到就**拒绝**并提示带上 `table`，不猜；
- 带 `table` 时在该表解析；**链接不跨 Database**（调用方的授权是按 Database 给的）；
- 拒绝：指向自己、目标不存在、目标不是 live、空 id、重复 id（去重后归一）。

引擎 diff 出增删，**同一事务两面都写**：新增时对面那行是被动地**增量追加**一条指向本行的条目
（revision +1、写 history），**绝不按本行的快照重算对面**——重算会把对面其他的链接抹掉。
对面写完后的 revision 才记进本行的条目，否则摘要一写就自判陈旧。

读取：`SELECT` 的结果里带 `links`（与 `route_paths` 同位置），每条含对面 row_id、表、摘要与
摘要取自哪个 revision；事实仍按 `row_id` 点查。链接是库里唯一的双写冗余，所以
**两面一致进了不变量断言**：每个 live 行出边都要有对面的回边，悬空或单边都算违例，
`doctor` 报 `broken_links`。

## 修复队列（M6b-1 已实现）

懒修复要一个**持久队列**，它就是一张普通表 `mem_repairs`，主键是「端点」
`(table_id, row_id, counterpart_table_id, counterpart_row_id)`，所以同一个端点重复入队是空操作、
崩溃后重启也还在。原因有两类：`stale_summary`（存的 revision ≠ 对面当前 revision）、
`stale_reference`（对面已被 `superseded`，引用要改指接替者）。

**入队主力是写方，不是读方**：拆分／合并那次事务里，顺着源行**自己保留的** `links`
把所有指向它的端点一并入队——同事务原子提交，崩溃后不会留下「孤儿陈旧链接」。
读路径只做补漏（`stale` 标记 + 该读事务结束后的短写入队）。
**源行的 `links` 绝不能清空**：那会同时毁掉回指与修复所需的反向清单。

**不变量据此弱化**（不是删掉）：指向 `superseded` 的行**且队列里有对应待修条目** → 合法；
指向 `superseded` 却**不在队列** → 违例；「对面有回指」仍然必须成立。没有这条弱化，
任何被链接过的行都无法再被拆分——M6a 落地时正是这个状态，M6b-1 修掉的就是它。

**摘要入队也在写方**：一次原地写入会推进这一行的 revision，于是所有指向它的摘要都过期——
写的时候顺着自己保留的 `links` 把它们排队（刚被这次写入刷新过的那几端跳过，否则一次链接写入
会给自己排一个修复）。

## 出队（M6b-2 已实现）

```sql
REPAIR LINKS IN DATABASE work LIMIT 64;
```

- **有界**：批大小就是语句的 `LIMIT`，并且必须 ≤ 调用方声明的 `max_affected_rows`；
  后台 worker 只是同一入口的调度壳（默认关闭，保证测试确定性）；
- **出队时重新校验**：队列记的是写入那一刻的事实。持有行没了、条目已不成立 → **丢弃**
  而不是照着旧条目盲写；
- **`stale_reference` 修复**：沿 `successor_ids` 走到**链尾**（去重、防环），去掉旧行上的反向边，
  给每个终点接替者补上双向链接，持有行的引用改指全部接替者；
- **`stale_summary` 修复**：以对面当前 revision 重写摘要，**并且两面摘要一起写**
  （先算出两边的新 revision，再各自写入），否则「修一次 → 对面又陈旧 → 再入队」会自激；
- **修复本身不入队**：它直接落行，不走写方的入队路径。

读侧不再需要额外的 `stale` 标记：写方入队已经覆盖了「内容变了」，而链接写入自己会刷新两端——
所以不存在"没人访问就永远不修"的窗口。

## 摘要懒更新

对方行原地修改后，不去同步改所有链到它的行：

- 读到链接时比较存下的 `revision` 与对方当前 revision，不一致即摘要过期；
- 过期时照常返回（摘要只是提示，事实以回表为准），并把「刷新摘要」放进修复队列，
  与废弃行的懒更新共用一个队列；
- 刷新是普通的原地修改，照常写 history。

## 不做的

- **不设链接类型**：没有 `relation_type`、`description`，链接只有对方 RowID、摘要和 revision；
- **不设上限**：链接条数与摘要长度都不限；
- **history 不特殊处理**：加链接、删链接、刷新摘要都是对数据行的原地修改，照常记。

## 引擎前提

链接与摘要不设上限。行正文是 SQLite TEXT，大行由 SQLite 自己存，
本项目不实现 Overflow Page。
