# Memora 架构原则

状态：**最高产品参考规范**（2026-08-22）。与[写入形态](./write-model.md)、
[查询形态](./query-model.md)并列，同在[产品宪章](./ai-native-product-charter.md)之下。
宪章管**产品是什么**，写入/查询形态管**数据怎么落库、怎么被找到**，
本文管**代码与结构怎么组织**。与本文冲突的实现要改实现，不是改本文。

四条原则。每条给出**判据**——怎么算违反——因为没有判据的原则等于没有原则。

## 一、高内聚低耦合，整体简洁清晰

一个组件应该只对一件事负责，并且把那件事负责到底。

### 判据

违反的信号，按可判定性排序：

1. **一次逻辑操作横跨多个互不保证原子性的事务域。** 提交一半失败时，
   系统需要"毒化标记"或"阶段 checkpoint"才能说清自己在哪——
   那是耦合的症状，不是解决方案；
2. **上层 import 下层的实现细节**，而不是经由一个用领域词汇写成的接口；
3. **同一个失败会以两种不同形态出现**（比如投影失败让写入失败，
   而索引失败让发布中毒），说明两件事被绑在了一起。

### 已知实例

- **一次 row INSERT 碰约 15 样东西**，横跨两个事务域：`nativestore.File` 事务里
  写闸、Catalog 读、RowID、两个序列计数器、Row 记录、History 记录、
  membership 记录、change envelope；`commit()` **之后** `PublishMutation`
  再碰三棵各自独立 `treecommit`/WAL 的树（versions／fulltext／current）、
  四次 phase checkpoint、失败时 `poisonPublication`。两个域之间没有原子性。

  好消息是**耦合方向本来是对的**：`nativerow`／`nativemutation` 不 import 任何
  检索包，只经 `PageAuthority` 接口。真正的耦合点集中在 `pagestoremigration`。

- **现成的解耦模板就在仓库里**：`authorityChangeTree.reconcile` —— 变更日志驱动、
  游标推进、批量、读时惰性触发地重放进 `changeindex`。派生索引若都照它走，
  写入事务就只剩"写自己的数据"。

细目与证据见[架构审计](../development/architecture-audit-2026-08.md)。

## 二、能用一张表解决的，就别造复杂逻辑

一个"甲和乙有关系"的事实，用一张表 + 必要的索引表达。
不要为它单造一种带自己版本号、自己墓碑、自己正反双向记录的对象类型。

### 判据

出现下面任意一条，就该问"这是不是本该是一张表"：

1. 一种记录类型**只用来表达两个东西之间的对应关系**，却自带 revision 与
   `Deleted` 墓碑；
2. 同一份事实**存了两遍**（正向一份、反向一份，或按行一份、按事务一份），
   于是需要一致性校验、需要健康扫描去发现两份对不上；
3. 存在一类线上问题，**只可能因为这份冗余而发生**——
   "指向过期版本"、"作用域对不上"、"一个位置挂了两个东西"都属此类。

第 3 条最有力：**结构性消除一类 bug，胜过为它写扫描与修复工具。**

### 已知实例

- **History**：曾是每行每版本一条独立记录，与变更日志的事务级归属重复。
  写入形态改为**每张业务表一张 history 表**，键 `(row_id, 序号)`，
  读一行的完整历史一次范围扫；
- **Membership**：曾是带 `MembershipRevision` 与墓碑、正反两个 object kind
  的独立关系。改为**叶子直接挂 RowID** + 一棵反向索引树。
  这一改让三类语义健康问题（`stale_membership`、`invalid_membership_scope`、
  `multi_row_leaf`）**结构性消失**——不是修好了，是不可能发生了。
  见[叶子直挂 RowID](../storage/leaf-rowid-v1.md)。

**反过来的例子，同样属于本条**：history 从"一种对象"变成"一张表"是对的，
但表默认可查，于是"已删除 Row 的历史必须拿不到"这条规则就得**明写**，
否则新读面会一个一个漏——`SELECT ... AS OF` 就漏过一次。
用表简化结构的同时，要把原本由那套复杂逻辑顺带把住的关一并接过来。
见[查询形态 §7 删除的契约](./query-model.md)。

## 三、候选预测器只给路径

关键词检索与向量检索**只回答一件事**：命中的数据项在语义树的哪个位置。
返回完整语义树路径，**不做任何其他操作**。

### 判据

预测器的返回值里出现下列任何一样，就是越界：

- **分数**（score、score_kind、match_count、frequency、cosine、点积……）；
- **解释**（reason、matched_fields、predictor 回执、状态码）；
- **正文**，或任何免于回表就能当答案用的内容；
- **让调用方还得再做一步换算才能导航的东西**（裸 route_id、object_id、
  字符偏移）。

预测器也不得**代替调用方做动作**：不回表、不预取、不改写查询、不缓存结果。
它说"往这儿看"，然后结束。

### 为什么

语义树是唯一的导航权威（宪章）。预测器一旦返回分数和理由，
它就变成了第二个权威——调用方会开始比较分数、解释理由、按分数截断，
于是"候选预测器"悄悄变成了"检索引擎"。只返回路径，
这条路从结构上就走不通：路径只能拿去导航。

### 有界与取舍

- **`limit` 保留**：有界是宪章要求，不是分数的替代品；
- **去重保留**：同一路径只出现一次；
- **排序仍在内部做，只是不对外暴露。** 命中数超过 `limit` 时总得决定留哪些，
  现有的 `MatchCount` + specificity（route > table > database）与向量的点积
  top-K **保持不变**，只是不进返回值。对外按路径字典序稳定输出。

  这一条必须写明：不写，实现时必然各自发挥。

### 已知实例

现状与目标的完整对照、改动点与分阶段，见
[候选预测器只给路径](../query/predictor-path-only-v1.md)。

## 四、一切都要有物理存储，启动只给钩子，查的时候按需去文件里取

**任何与数据量相关的结构，都必须以物理形式存在于文件里。**
启动时只允许建立**指向它的钩子**——打开文件、读根页、拿到入口——
不允许把内容本身读进内存。要查的时候按需去文件里取。

这条管的是**常驻内存与数据量的关系**。前三条管结构怎么组织，这条管
结构住在哪里。它是四条里唯一一条会随时间**自动恶化**的：违反它的代码
今天跑得好好的，因为库还小。

### 判据

出现下面任意一条，就是违反：

1. 一个结构在**打开时被完整读进内存**，而它的大小与数据量（行数、
   版本数、节点数、历史写入次数）相关；
2. 一个查询的代价与**库里有多少东西**相关，而不是与**它要的那些东西**相关——
   `Enumerations()` 计数器就是为这一条设的护栏；
3. 一个内存结构**没有容量、没有淘汰**，却不是 cache 而是**唯一的索引**——
   也就是说，丢了它就找不到数据。这条最严重：它意味着那份「物理存储」
   其实并不完整，真正的索引只活在内存里。

**有界的常驻结构不算违反**：buffer pool 有容量有淘汰，是 cache；
schema 定义随表数增长而表数有人管，那是有界的。判据里的「与数据量相关」
指的是**用户数据的量**，不是配置的量。

### 为什么

一个个人库的数据量没有上限——它就是要一直写下去。任何正比于「写过多少」
的常驻结构，都意味着这个库有一个**它自己不知道的寿命上限**：
到某个数据量就打不开了。而这个上限不会在开发时暴露，只会在用户那里暴露。

「按需去文件里取」听起来更慢。它不是：一次点查是一次 `ReadAt`，
操作系统的 page cache 会替我们缓存热数据，而那份缓存**有淘汰、有上界**。
把全部索引常驻内存换来的不是速度，是一个不受控的内存曲线。

### 已知实例

**`nativestore.File.records` 是当前最严重的一处，也是唯一命中第 3 条判据的。**
它是 `map[{kind, id}] → {offset, length, CRC, schema}`，
`Open()` 时 `scan()` 从头读完整个文件建起来。**没有容量、没有淘汰，
而且是这个文件唯一的物理索引**——给定 (kind, id) 只有它知道字节在哪。

由于每个版本是一条独立记录，它随**历史上写过多少次**增长，不随活跃数据增长。
一行改 100 次就是 100 个永不释放的条目。

消除进度（对象按「索引在哪」分）：

| 对象 | 现状 | 状态 |
| --- | --- | --- |
| Row（当前 / 历史） | 每表聚簇树 / 每表 history 树 | ✅ 已消除（E4／E5） |
| 两种 Membership | 对象已整个删除 | ✅ 已消除（E3） |
| History | 已并进 history 树 | ✅ 已消除（E5） |
| Database／Table／Column | catalog 树 **+ 内存表** | ⚠️ 树有了，内存表还在 |
| **Route（语义树）** | **objects 树（叶子存正文）** | ✅ 已消除（E7 阶段 2） |
| Relation | 仅内存表 | ❌ 未做 |
| Configuration／SnapshotMeta／Opaque | 仅内存表 | ❌ 未做 |

无界的那一族（Row）已经搬完，这是过去这一轮存储改造的实际收益。
Route 随后跟上：点查是一次 B+ 树下降，整树遍历是一个 kind 的范围扫，
`Enumerations()` 在 Route 读面归零。**剩下的是 Relation 与那一族小对象，
以及 Catalog 的正文**；记录文件本身的 `scan` 要降级为修复路径才算收尾。

### 一处必须一起解决的循环依赖

把 `File.records` 换成树，会撞上一个顺序问题：**generation 里的树是从记录
文件派生的**。如果读记录文件需要一棵住在 generation 里的树，那么派生结构
就成了读取权威结构的前提——一个可以被整个删掉重建的东西，变成了打不开库
就恢复不了的东西。

所以记录文件要有**它自己的**持久索引，与 generation 分开、随它一起被视为
权威；generation 仍然只是派生。设计这一条时不能绕过去。
