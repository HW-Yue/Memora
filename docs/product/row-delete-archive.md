# 行删除：归档后物理删除

状态：**讨论稿**（2026-09-21 定方向；一行多叶与入向链接两处待定）。
取代[数据行的生命周期](./row-lifecycle-successor.md)里「删除只置 deprecated、废弃行留在主表」，
并修订[查询形态](./query-model.md) §7「判据是可达性，不是物理擦除」。

## 一句话

DELETE = 先把删除前的语义路径与内容写进**归档表**，再把行、它的叶子、因此变空的父节点
和它的 history **真删掉**。恢复不由引擎做。

## 一次删除（一个事务）

1. **归档**：写入归档表——删除前的完整语义树路径（逐段 `route_id` / `name` / `kind` /
   `purpose`）、被删行与相关语义节点的完整内容；
2. **删行**：主表整行删除，`route_leaf_ids` 等默认字段随行消失；
3. **删叶**：这条行占用的叶子节点删除；
4. **剪枝**：自底向上——摘掉这个子节点后父节点**没有其它子节点**，连父节点一起删并
   继续向上；父节点还有其它子节点，就只把该 id 从 `child_ids` 摘掉，到此为止；
5. **删 history**：这条行 `(row_id, *)` 的全部记录删除，**不归档**。

五步同一个 SQLite 事务，任何一步失败整体回滚。

## 恢复

**引擎不提供恢复入口。** 归档表是引擎逻辑的终点；Agent 读归档表自己重建行与语义路径。
归档内容因此必须自足到「Agent 拿它就能建回来」：路径逐段带 ID，节点与行的内容完整。

## 未决

- **一行多叶**：一行可挂在多个叶子下。删除时是删掉它占用的**全部**叶子（各自剪枝），
  还是只删指定的那一个语义索引；
- **入向链接**：别的行用 `links` 指着被删行时怎么办。现有规范要求链接两面一致，
  而归档式删除之后被删行不再存在——是同一事务摘掉对面那一面，还是留悬空交给 Agent；
- **归档表是新的读面**：[查询形态 §7](./query-model.md) 的可达性清单要加它一行。
