# 行删除：归档后物理删除

状态：**写侧已实现**（2026-09-21）；**归档读面待做**（`SHOW ARCHIVE` / `OPEN ARCHIVE`）。
取代[数据行的生命周期](./row-lifecycle-successor.md)里「删除只置 deprecated、废弃行留在主表」，
并修订[查询形态](./query-model.md) §7「判据是可达性，不是物理擦除」。

## 一句话

DELETE = 先把删除前的语义路径与内容写进**归档表**，再把行、**它那一个叶子**、因此变空的
父节点、别人指向它的链接和它的 history **真删掉**。恢复不由引擎做。

挂载是 1:1（[写入形态](./write-model.md) §1.3）：一行只占一个叶子，一次删除只对应一条
叶子路径，不存在「删哪些叶子」的选择。

## 一次删除（一个事务）

1. **归档**：写入归档表——删除前的完整语义树路径（逐段 `route_id` / `name` / `kind` /
   `purpose`）、被删行与相关语义节点的完整内容；
2. **删行**：主表整行删除，`route_leaf_id` 等默认字段随行消失；
3. **删叶**：这条行占用的那个叶子节点删除；
4. **剪枝**：按[Route 配套表](./route-companion-table.md)「没有接替者的变空就物理删除、
   并递归向上」的通用规则做——这是它的一个触发面，不是删除专属逻辑；
5. **摘链接**：链接两面都存，**被删行自己的 `links` 就是「谁指向我」的清单**。逐个到
   对面行里把指向被删行的这一条删掉；对面行照常 `revision + 1`、写 history
   （这仍是原地修改，见 [history 谱系](./history-lineage.md)）。不靠扫全库找悬空链接；
6. **删 history**：这条行 `(row_id, *)` 的全部记录删除，**不归档**。

六步同一个 SQLite 事务，任何一步失败整体回滚；删除成功时不留悬空链接。

## 恢复

**引擎不提供恢复入口。** 归档表是引擎逻辑的终点；Agent 读归档表自己重建行与语义路径。
归档内容因此必须自足到「Agent 拿它就能建回来」：路径逐段带 ID（**含 root**，重建也需要它的
purpose），节点与行的内容完整，删除前的双向链接也在快照里。
被摘掉的对面链接不在归档语义内——恢复是重建，不是回滚现场。

读面形状（顾问判形，**待实现**）：`SHOW ARCHIVE`（只列元数据，必须带过滤／分页，不能无条件
全列，否则退化成软删除浏览器）与 `OPEN ARCHIVE <id>`（取全量内容）。不给 `SELECT`／
`OPEN ROUTE` 加参数——参数化等于把归档挂进普通查询语法树，`WHERE`／`JOIN` 一来就成旁路。
归档表仍是 `mem_` 内部表，不出现在 `SHOW`／`DESCRIBE` 里，只由这两条语句触达。

## 级联写的预算口径（已定，2026-09-21）

第 5 步会写别的行，而 `max_affected_rows` 与结果信封现在只算目标行。口径分三层：

1. **guard 保持「目标行」语义**：`max_affected_rows` 校验的是 Agent 声明要动的行
   （DELETE 为 1），**不因级联变大而被拒**——否则一次正常的删除会随"别人链了它多少"随机失败；
2. **级联另设界**：单次删除能摘的链接条数上限 = **1000**（`maxCascadeDetach`，与
   `max_query_scan` 同量级），超界 `constraint_violation` 并让 Agent 分步清理。
   有界是宪章硬要求，级联不能例外；
3. **结果如实报数**：`affected_rows` 仍是目标行；级联改了哪些行**已进 `mem_changes`**
   （变更条目的 `related_object_ids`），进结果信封随读面一起做——链接现在还没有写入口，
   级联数在 M6 之前恒为 0。
