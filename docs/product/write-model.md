# Memora 写入形态

状态：**最高产品参考规范**（2026-08-22）。本文是写入与恢复形态的权威产品规范，
描述：history 作为独立表、语义索引叶子直接挂 RowID、三份日志各司其职、
binlog 作为唯一恢复依据。与本规范冲突时，以本文为准。

## 1. 核心模型

三个基本构件：

1. **业务表**：真实数据的存储。每张表 = 一棵独立的 B+ 树（聚簇表）。除业务列外，
   必须带一个 `history_id` 字段，指向本行的最新一条 history 记录；后期拿着它直接查
   这条数据的来龙去脉。
2. **history 表**：每张业务表对应一张 history 表（如 `notes` ↔ `notes_history`）。
   history 表同样是**一棵独立的 B+ 树**。每次写入（INSERT/UPDATE/DELETE）在 history
   表里追加一条记录，存"这次改动是谁、从哪、为什么、什么时候、从什么改成什么"。

   **history 表的键是 `(row_id, 序号)`**，序号在同一 row_id 内递增。这样同一行的全部
   变更在 B+ 树里物理相邻，读一行的完整历史是**一次范围扫**（顺叶子链连续读），
   不是一条条点查。`history_id` = 这个复合键，业务表存的是最新一条的键——它是
   "从这行直接跳到它最近一次改动"的方便入口，不是读历史的唯一通路，
   也不需要 history 记录之间再互相串指针。

   **Row 被删除后，它在 history 表的整个 `(row_id, *)` 区段一并不可达。**
   history 是一张真的表，而表默认是可查的——所以这条必须明写：删除的契约是
   "从任何地方都拿不到"，history 表不是例外。物理上留不留那些行无所谓，
   拿不到才是承诺。完整清单见[查询形态 §7](./query-model.md)。
3. **语义索引树**：叶子节点**直接挂 RowID**（不再有独立的 membership 对应关系）。
   找到叶子 = 找到它下面的 RowID；RowID 指向业务表里那条真实数据。

   **这个挂载是双向的**：业务行同时带一个默认字段 `route_leaf_ids`，
   存它挂在哪些叶子下。写入本来就是「分配 RowID → 挂到叶子 → 再写数据」
   （见第 2 节），**写数据那一刻挂载已经确定**，直接填进去即可——
   不需要再造一个结构去回答一个写入时已知的问题。

   **两边都只存稳定 ID，谁都不存路径。** 语义树会被频繁重构
   （SPLIT／MERGE／改名都是常规操作），任何记下来的路径都会过期。
   要完整语义树路径时，从叶子顺父节点指针往上走，**实时算**。

   这两份指向是「同一份事实存两遍」的一个**有意例外**
   （见[架构原则](./architecture-principles.md) §2）：两边在同一次写入的
   同一个事务里落盘，换来两个方向都零额外结构。例外要写明，不能默认。

## 2. 写入前置：语义定位与 RowID 分配

写入不是"拿到数据直接塞进表"，而是先回答"这条数据该属于哪个语义位置"。

1. **意图识别**：理解本次要写入的是什么内容。
2. **查语义索引**：进入已有语义索引树，逐层找有没有已经存在的、对应当前要写入内容的
   叶子（查重）。如果命中，走修订/合并，而不是新建。
3. **选位置**：如果没有命中，在合适的非叶子节点下面，选一个位置新建一个叶子节点。
4. **分配 RowID**：调用一个分配接口，拿到下一个尚未使用的 RowID。**RowID 按表递增**
   ——每张表（含 history 表）各自维护自己的递增序列，不从全局共用一个计数。
5. **挂载**：把这个 RowID **直接接在新建的叶子节点下面**。语义索引叶子此时 = 这个
   RowID 的导航入口。
6. **写入真实数据**：数据落业务表（进入第 3 节），
   并把第 5 步确定的叶子 ID 一并写进行的 `route_leaf_ids` 字段——
   **挂载在这一步之前就已经确定，所以这是零成本的**，
   不需要事后再建结构去反查。

## 3. 写入流程（含日志与两阶段提交）

每次写入严格按以下顺序执行，缺一不可：

```text
① 写 change log          —— 记录"把某条数据改为某条数据"或"写入某条数据"（逻辑变更，事务回滚的 undo 依据）
② redolog：写 prepare     —— 物理日志，记录本次更改；先标 prepare
③ 写 binlog              —— 逻辑日志，记录本次数据更改（绑定业务表 + history 表）
④ redolog：prepare → commit —— binlog 写成功后，把 redolog 的 prepare 改为 commit
⑤ 写 history 表          —— 追加一条 history 记录，返回 history_id
⑥ 写业务表              —— 真实数据 + history_id 字段（指向第⑤步的 history_id）
```

顺序要点：

- **binlog 写成功后，才把 redolog 的 prepare 改成 commit**（两阶段提交）。崩溃发生在
  prepare 阶段 → 该事务未提交，回滚；发生在 commit 之后 → 事务已提交，按 binlog 恢复。
- **每次更改同时绑定两张表**：业务表（真实数据）和 history 表（变更记录），两者一起改。
- **binlog 记录的是"本次数据更改"**，不是 SQL。原因：要保证记录的时间是最初写入的时间，
  不能等到 SQL 执行时才打时间戳。
- **history 表也写在 binlog 里**——后期重建时，history 表从 binlog 重建出来即可。

## 4. 写入时的语义索引维护

写入不是永远新建一个叶子。按语义定位查重命中就复用；写入过程可能触发拆分与合并，
这些是写入形态的一部分：

### 4.1 叶子已存在：复用或修订，不新建

- 查语义索引命中已有叶子（语义对应）→ 走修订或合并，不新建、不改写无关数据；
- 只有没有命中时才新建叶子（见第 2 节）。

### 4.2 内容太大：语义拆分，不机械切割

- 一条数据包含两个可独立修改的主题、内容超预算时，**不截断、不盲目调大上限**；
- 语义拆分：生成多个各自完整的数据 → 原数据标为被替代 → 重分配 history 与叶子挂载
  → 必要时拆分上层语义节点 → **一次事务提交**；
- 合并执行相反流程，同样不能只改正文而留下陈旧的语义索引。

### 4.3 分支太挤：fan-out 超限，二选一

- 一个父节点下的 live 子节点数超过 `branch_fanout`（默认 12）时，**新增一律失败**，
  不是警告、不是分页、不是带理由的例外；
- 失败给出两条互斥出路，由 Agent 判断走哪条：
  - **重构子树**：合并、下沉或拆分节点，让新节点归入已有分组；
  - **提高本库上限**：`ALTER CONFIGURATION ROUTE_POLICY SET BRANCH_FANOUT :n`，
    一次最多 +4（加宽语义树需要反复判断）；
- 引擎不替 Agent 选，只保证上限可发现、越界必然失败、两条出路都可执行。

### 4.4 叶子只挂一条数据

- 一个叶子最多挂一个活跃 Row（单行叶子）。叶子已占用时，语义上应新建叶子
  （同一 Row 可以属于多个叶子），而不是往已占用的叶子继续挂。

## 5. 日志体系：三份日志各司其职

| 日志 | 内容 | 职责 | 恢复时 |
|------|------|------|--------|
| **change log** | 逻辑变更（某数据从 A 改为 B / 写入某数据） | **事务回滚的 undo 依据** | 不做崩溃恢复依据 |
| **redolog** | 物理日志，`prepare`/`commit` 两字段 | 崩溃时保证事务原子性（判断哪些事务该提交/回滚） | 只用来判定提交状态 |
| **binlog** | 逻辑数据更改（含 history 表） | **唯一恢复依据** | 唯一的重建来源 |

**核心原则：binlog 是后期恢复的唯一依据，就这一个就够了。** 不管是备份、恢复还是其他
场景，都只依赖 binlog；change log 和 redolog 不参与恢复重建。history 表也在 binlog 里，
后期重建时从 binlog 一并恢复。**change log 的职责是事务回滚（undo）**：事务中途失败或
主动回滚时，按它把业务表、history 表恢复到改动前。

## 6. 崩溃恢复

- 崩溃后，先看 **redolog** 的标记：事务停在 `prepare`（binlog 未写完）→ 未提交，丢弃；
  事务已 `commit`（binlog 已写完）→ 已提交，按 binlog 重放。
- **重放 binlog** 作为唯一依据，重建：
  - 业务表当前数据；
  - history 表（binlog 里有它的写入）；
  - 语义索引挂载（叶子 ↔ RowID 关系）。
- 不需要第二套恢复机制，也不依赖 change log / redolog 重放业务数据。

## 7. 读取路径

- **读真实数据**：语义索引叶子 → RowID → 业务表，取当前值。
- **读历史**：拿业务表的 `row_id` 在 history 表按 `(row_id, *)` 做**范围扫**，
  一次拿到这条数据从创建到现在的全部变更记录，按序号有序。
  业务表的 `history_id` 是"只想看最近一次改动"时的直接点查入口。

## 8. 与当前实现的关系

当前 memora 的写入是：Row 本体 + 独立 ObjectKindHistory + 独立 membership 记录 +
Change Log。本设计 v2 的对应变化：

| 现状 | v2 目标 |
|------|---------|
| history 是独立 ObjectKindHistory 记录 | **history 变成一张表**，每业务表一张，走 B+ 树 |
| 语义索引叶子不含 RowID，靠 membership 关联 | **叶子直接挂 RowID**，去掉独立 membership |
| 业务表不含 provenance 引用 | 业务表带 **`history_id`** 字段，直接指向 history |
| 恢复依赖 Change Log + 快照 | **binlog 唯一恢复依据**，redolog 管提交原子性，change log 只审查 |

## 已确认

- 三份日志（change log / redolog / binlog）**全部保留**，职责分开：change log 管事务
  回滚、redolog 管崩溃原子性、binlog 管恢复。
- 每张表（业务表与 history 表）各是一棵独立的 B+ 树。
- RowID **按表递增**分配。
- history 表键为 `(row_id, 序号)`；读一行的完整历史走**范围扫**，业务表的
  `history_id` 是最近一次改动的点查入口，不承担串联全部版本的职责。
- **通用原则：能用一张表 + 必要索引表达的关系，就用表。** 不为一个"甲和乙有
  对应关系"的事实另造一种带自己版本号、自己墓碑、自己正反双向记录的对象类型。
  本文里 history 独立成表、语义索引叶子直接挂 RowID 是它的两个实例；
  判据见[架构原则](./architecture-principles.md) §2。
- 语义索引的挂载是**双向**的：叶子存 RowID，业务行存 `route_leaf_ids`。
  两边都只存稳定 ID，**都不存路径**——路径顺父节点指针实时算，
  因为语义树会被频繁重构。
