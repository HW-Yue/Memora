# Memora 写入形态

状态：**最高产品参考规范**（2026-09-20）。持久化基座是 SQLite（[ADR-0011](../decisions/0011-pure-storage-engine-tables-everything.md)）。与本规范冲突时以本文为准。

## 1. 核心模型：三张表

每张业务表建立时，自动带两张配套表（角色记在 Catalog 上，**Agent 只看见数据表**）：

| 角色 | 现役表名 | 内容 |
|---|---|---|
| 数据表 | `data_<tableID>` | 真实数据当前值 |
| history 表 | `history_<tableID>` | 该表每一行的全部变更记录 |
| 语义配套表 | `routes_<tableID>` | 该表的语义索引树 |

三张都是**普通 SQLite 表**。引擎对它们一视同仁，区别只在 Catalog 的角色标记。

### 1.1 数据表

除业务列（存于 `values_json`）外带若干默认字段：`row_id`、`revision`、`row_state`、
`route_leaf_id`、`links`、`successor_ids`、`ordinal`、时间戳。

`row_id` 是随机稳定 ID，永不复用；`ordinal` 是每张表各自递增的序号，带索引，
用于稳定排序与游标翻页。

### 1.2 history 表

主键是 **`(row_id, revision)`**。同一行的全部变更因此在主键上物理相邻，
读一行完整历史是**一次范围扫**并按 revision 有序，不是逐条点查。

数据行自己带 `revision`，所以数据表**不需要**额外的 `history_id` 指针——
`(row_id, revision)` 本身就是「跳到这行最近一次改动」的键。

history 只记**原地修改**。拆分、合并产生的新行各建自己的 history 并
**指向来源 history**，源行的 history 不因身份变化而增长，见 [history 谱系](./history-lineage.md)；
源行仍留主表、用一个字段记录新 row id，读时懒解析，见[数据行的生命周期](./row-lifecycle-successor.md)。

**删除已改为归档后物理删除**（2026-09-21）：删除前的语义路径与内容先进归档表，
再删行、删叶、剪掉因此变空的父节点、删除该行的 history。见[行删除](./row-delete-archive.md)。
删除的契约仍是「从任何地方都拿不到」，归档表是唯一例外读面，完整清单见[查询形态 §7](./query-model.md)。

### 1.3 语义配套表

叶子**直接挂 RowID**，没有独立的 membership 对应关系。找到叶子 = 找到它下面的 RowID。
细节见 [Route 配套表](./route-companion-table.md)。

**挂载是双向的**：数据行同时带 `route_leaf_id`，存它挂在哪个叶子上。写入本来就是
「分配 RowID → 挂到叶子 → 再写数据」，写数据那一刻挂载已经确定，直接填进去即可。

**一行只占一个叶子（1:1）。** 一个叶子最多挂一个活跃 Row，一行也只属于一个叶子。
`route_leaf_id` 是单值，未挂载用空串表示，不用 NULL。

**两边都只存稳定 ID，谁都不存路径。** 语义树会被频繁重构（SPLIT／MERGE／改名都是
常规操作），任何记下来的路径都会过期；要完整路径时顺父节点实时算。

这两份指向是「同一份事实存两遍」的一个**有意例外**（见[架构原则](./architecture-principles.md) §2）：
两边在同一个事务里落盘。1:1 之后例外的正当性比过去更强——两边都是标量，
一致性成了一条**可判定的等式**（`leaf.row_id = r` 且 `row.route_leaf_id = leaf`），
可以断言、可以校验，而不是一份要同步的列表关系。

## 2. 写入前置：语义定位与 RowID 分配

写入不是「拿到数据直接塞进表」，而是先回答「这条数据该属于哪个语义位置」。

1. **意图识别**：理解本次要写入的是什么内容；
2. **查语义索引**：找有没有已存在、对应当前内容的叶子（查重）。命中则走修订／合并；
3. **选位置**：未命中时，在合适的非叶子节点下新建一个叶子；
4. **分配 RowID**：取一个未使用的稳定 `row_id`；
5. **挂载**：把该 RowID 接在叶子下，叶子即该 Row 的导航入口；
6. **写入真实数据**：数据落数据表，并把第 5 步的叶子 ID 写进 `route_leaf_id`——
   挂载在此之前已确定，所以这是零成本的。

## 3. 写入流程：一个事务

一次写入是**一个 SQLite 事务**，内含：

```text
① 追加 history 行         —— history_<id>，键 (row_id, revision)
② 写/改数据行             —— data_<id>，含 revision 与 route_leaf_id
③ 写语义配套表            —— routes_<id>，父子两面一致
④ 追加变更记录            —— mem_changes：谁改的、为什么、什么时候
```

四步全成功才提交，任何一步失败整体回滚。**原子性、回滚与崩溃恢复由 SQLite 承担**：
本项目不写 redo/undo 日志，不做两阶段提交，也没有自己的恢复重放器。

写事务串行执行，读只看最后一次提交——不做 MVCC，没有快照或 read view。

## 4. 写入时的语义索引维护

写入不是永远新建一个叶子。查重命中就复用；写入过程可能触发拆分与合并，
这些是写入形态的一部分。

### 4.1 叶子已存在：复用或修订，不新建

命中已有叶子（语义对应）→ 走修订或合并，不新建、不改写无关数据。
只有没有命中时才新建叶子。

### 4.2 内容太大：语义拆分，不机械切割

一条数据包含两个可独立修改的主题、或超出内容预算时，**不截断、不盲目调大上限**。
语义拆分：生成多个各自完整的数据 → 原数据标为被替代（`successor_ids`）→
重分配 history 与叶子挂载 → 必要时拆分上层语义节点 → **一次事务提交**。
合并执行相反流程，同样不能只改正文而留下陈旧的语义索引。

### 4.3 分支太挤：fan-out 超限，二选一

一个父节点下的 live 子节点数超过 `branch_fanout`（默认 12）时，**新增一律失败**，
不是警告、不是分页、不是带理由的例外。失败给出两条互斥出路，由 Agent 判断：

- **重构子树**：合并、下沉或拆分节点，让新节点归入已有分组；
- **提高本库上限**：`ALTER CONFIGURATION ROUTE_POLICY SET BRANCH_FANOUT :n`，
  一次最多 +4（加宽语义树需要反复判断）。

引擎不替 Agent 选，只保证上限可发现、越界必然失败、两条出路都可执行。
规则见上文 §4.3。

### 4.4 一叶一行，一行一叶

一个叶子最多挂一个活跃 Row，一行也只占一个叶子。叶子已占用时应新建叶子，
而不是往已占用的叶子继续挂；同一行也不会同时挂在两个叶子下。

## 5. 变更记录

`mem_changes` 是普通表，记录每个事务改了什么、谁改的、为什么、什么时候，
与数据、history 在同一事务里写。它是**审计与追溯**面，**不承担 undo**
——回滚由 SQLite 事务负责。

## 6. 恢复与备份

崩溃一致性由 SQLite 保证，本项目不实现恢复重放。备份与迁移走文件级复制或逻辑导出，
不依赖自研日志。

## 7. 读取路径

- **读真实数据**：定位到 RowID，再回数据表点查取当前值。定位四条路——
  语义索引（Agent 主路）、关键词召回、向量召回、Skill 层 jev，
  见 [查询形态](./query-model.md) 与
  [检索路线](../query/retrieval-routes-jev.md)；
- **读历史**：拿 `row_id` 在 history 表按 `(row_id, *)` 范围扫，一次拿到全部变更，
  按 revision 有序。

## 已确认

- 三张表：数据表、history 表、语义配套表，全是普通 SQLite 表，角色记在 Catalog；
- `row_id` 稳定随机、永不复用；`ordinal` 每表递增，供稳定排序与翻页；
- history 键 `(row_id, revision)`，读全历史走范围扫；数据行自带 revision，
  因此不需要额外的 history 指针字段；
- 一次写入 = 一个 SQLite 事务；不做 MVCC；不自写日志与恢复；
- **通用原则：能用一张表 + 必要索引表达的关系，就用表。** 不为一个「甲和乙有对应关系」
  的事实另造一种带自己版本号、墓碑、正反双向记录的对象类型。判据见
  [架构原则](./architecture-principles.md) §2；
- 语义索引挂载**双向**：叶子存 RowID，数据行存 `route_leaf_id`，两边都不存路径；
  一行只占一个叶子（1:1）；
- **已定（2026-09-21）：删除 = 归档后物理删除**，见[行删除](./row-delete-archive.md)；
  拆分/合并的新行 history 指向来源 history，见 [history 谱系](./history-lineage.md)。
