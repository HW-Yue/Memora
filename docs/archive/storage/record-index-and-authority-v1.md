# 记录文件的索引与权威:聚簇转正,已完成

状态:**已裁定(2026-09-02)、已完成(2026-09-13)**。落实
[架构原则](../../product/architecture-principles.md)**第四条**收尾。
本文并排写了两条路各放弃什么,**§5 裁定走 C(聚簇转正)**;
路 B 保留是为了留下比较的依据,不是备选项。
不是独立规范:与架构原则冲突时以架构原则为准。

编写原则同[存储层总览](./README.md):每条「现状」断言都能指到具体文件与行。

## 0. 这份文档取代了什么

[物理索引](./physical-index-v1.md)阶段 5。原文只写了其中一条路(游标 + 增量扫),
把它当成唯一解。实际有两条,本文并排量过之后裁定走 C(§5)。

## 1. 要解决的是什么(已量,不是猜)

开库时 `nativestore.File.scan()`(`store/native/file.go:580`)从头读完整个记录
文件,逐条校验,建起 `File.records` ——一张 `map[{kind,id}] → {偏移,长度,CRC}`。

实测(每条 400 字节):

| 历史写入条数 | 开库耗时 | 常驻表 |
|---|---|---|
| 1 万 | 128 ms | 6.1 MiB |
| 5 万 | 422 ms | 8.9 MiB |
| 20 万 | **1.34 s** | **27.5 MiB** |

**两列都随「历史上写过多少次」增长,不随「现在有多少数据」。** 一行改 100 次
就是 100 个永不释放的条目。这是四条准则里唯一一条**会随时间自动恶化**的违反。

**做完之后同样条件复量(2026-09-13,`887c652`)**:20 万次写入 =
**53 µs / 1.4 KB**。开库现在只读文件头加旁边一个 16 字节的 commit hint,
两个数都不随任何东西增长。门是
`store/native` 的 `TestOpeningDoesNotGrowWithHowOftenTheDatabaseWasWritten`。

## 2. 一个必须先说清的事实:今天是聚簇 + 重复

容易搞错,所以摆在前面。今天**不是**「一个文件存数据、一个文件存索引」:

- 树是**聚簇**的,叶子里存的就是正文
  (`rowversionindex/codec.go:55`「Body is the encoded Row itself」;
  `objectindex` 的 `Record` 带 `Body`);
- **记录文件里同样存着一份完整的**。

也就是**数据存了两遍**,其中记录文件那份被宣布为权威。
[物理索引](./physical-index-v1.md)当初选聚簇时写明了这个代价
(「正文在记录文件与树里各有一份」),只是那时还没到收尾。

顺带纠正一个说法上的坑:**按 ID 建键的 B+ 树是持久的、唯一的索引结构,
不是「派生」的东西**。派生的是**语义树**(Route)——它不持有内容,是 Row 之上
的导航覆盖层。「generation 是派生的」说的是**那一份特定实例可以重建**,
不是「B+ 树这种结构天生次一等」。

## 3. 已经走完的部分(两条路都用得上)

| 事实 | 证据 |
|---|---|
| 树的崩溃恢复已完全靠 WAL | `treecommit.OpenRuntime` → `wal.RecoverSegmentSet`,不读记录文件 |
| 正文已全在树叶子里 | Row 在 versions 树;Route／Relation／Catalog 在 objects 树 |
| 读路径已完全不碰记录文件 | `TestALiveWorkloadNeverSweepsTheRecordFile`:四次写加九个读面,`Enumerations()` 增量为零 |
| 拒重复 ID 树里已有 | 三个索引包共 16 处 `ErrConflict` |
| **非聚簇的原语已备好** | `File.Location`(`:534`)、`File.ReadAtLocation`(`:554`),写好、零调用方,当初就是为这条路留的 |

## 4. 两条路(比较用;结论见 §5)

### 路 B:非聚簇——数据文件 + 索引文件

记录文件旁边放一个 **B+ 树索引文件**,存 `(kind,id) → 偏移`。它就是
`File.records` 今天干的事,只是从内存里的 map 变成盘上的树。索引文件与记录
文件**一起算权威**,与 generation 无关——所以没有「派生结构成为读权威的前提」
这个圈。

- **数据存一份**(记录文件);树叶子里那些正文变成纯冗余(见下)
- **开库不再全扫**:点查是一次树下降 + 一次 `ReadAtLocation`
- **改动小、可逆**:不动提交点,不动 COW 重建那层保险
- **代价:放弃 compaction**。非聚簇的隐含前提是**偏移永久有效**,即记录永不
  移动。今天只追加、不回收,所以成立;一旦要回收被覆盖版本占的空间,
  索引里所有偏移全废
- **要一并裁定**:树叶子里的正文怎么办。留着 = 承认是快读缓存(数据仍存两遍);
  拿掉退回存 Locator = 把 E7 阶段 2／4 刚做的倒回去

### 路 C:聚簇转正——树叶子即数据,记录文件退出

提交点上移到树的 group commit;记录文件在正确性上多余。
**页文件 + redo 日志 = 数据库**,binlog + 快照 = 灾难恢复。

- **数据存一份**(树叶子);记录文件删除或降级为纯归档
- **开库不再全扫**:没有表要建
- **保留 compaction 自由**:不依赖偏移永久有效
- **代价一:双保险的底没了**。今天树坏了能整个删掉重建(本轮 generation 从 v6
  升到 v8、老库自动 COW 重建靠的就是这层)。转正后页损坏只能靠 binlog + 快照
- **代价二:generation 升版的语义要重新定义**。今天升版 = 老库静默 COW 重建,
  那是「派生」才有的自由;转正后必须是就地迁移或拒绝打开。**这是主要工作量**
- **不可逆**:拆掉 `reconcile` 与 COW 重建之后退不回来

## 5. 已裁定:走 C(聚簇转正)

**2026-09-02 定。** 原本把「要不要 compaction」当成一个待定的产品偏好,
所以并排摆了两条路。那个摆法是错的:两条路在空间回收上不是「多一个功能少一个
功能」的区别,**是能不能做的区别**。

- **聚簇**:删一行 = 叶子里少一条 entry。页空了或过疏,`btree/rebalance.go`
  就地合并/再平衡(`RebalanceMerged`),腾出来的页 ID 进
  `wal/tree_redo.go` 的 `RetiredPageIDs`,恢复时照样回放
  (`tree_recovery.go:307`),之后由 `Runtime.FreePageIDs()`
  (`treecommit/runtime.go:216`)交回去复用。**局部、增量、崩溃安全,
  而且这条链今天就已经在跑了**——五个索引包都在用;
- **只追加 + 偏移索引**:删一行 = 写一条墓碑,字节永远留在文件里。要回收就得
  重写整个文件,而**一旦记录移动,索引里每一个偏移全部失效**,等于连带重建整个
  索引。全局、停世界、不可增量,**而且一行都还没写**。

所以这不是「B 省事、C 讲究」。B 是把空间回收从「已经实现的日常动作」降级成
「一个不存在、且天然停世界的批处理」。**记录文件那份重复本来就是要消灭的东西,
不该反过来由它决定树的地位。**

裁定:**页文件(B+ 树)+ redo 日志 = 数据库本身,记录文件在正确性上变成多余的。**

B 保留在 §4 里不删,是为了留下这次比较的依据;**它不是备选项**。

## 6. 硬门:已验通(2026-09-13,`988ab7e`)

**灾难恢复链必须先于不可逆的那一步验通**,因为走 C 之后它是唯一的底——
记录文件不再兜着。门已经过,细节见[灾难恢复链](./disaster-recovery-v1.md)。

门验的是**库整个没了**:`databases` 目录删掉——记录文件与页文件一起——
只留 binlog,而且从副本回放,像归档出去的日志那样。恢复后逻辑快照哈希逐字
一致,并且能通过重建出来的树把 Row 读出来。
**只删页文件证明不了什么**:那样兜底的还是记录文件,而那正是转正要放弃的
东西。

**本文原先写的全量那一半是错的,已订正。** 原文说:

> **全量**:`nativesnapshot.Export`／`Import` 已有。

「已有」是清点,不是核实。跑完发现两半接不上:逻辑导入是走正常写路径重放
历史,变更序号从 1 重新分配、目录对象只留当前版本;binlog 里带的是当时真正
写下的记录 ID 与序号。基底停在变更 2、日志从 5 续,`changeindex` 的
`Bootstrap` 拒绝这个洞。这是两种格式的性质,不是能修的 bug,已钉成
`TestALogicalSnapshotIsNotARollforwardBase`。

全量那一半改成**记录日志的字节前缀**。逻辑快照仍是迁移与跨引擎比对的正确
工具,只是不能当前滚的基底。

## 6.5 做完之后:三件事变了

**提交点在树上。** 一次写是「记录日志 prepare(记录与 binlog 帧落盘,没有提交
标记)→ 三棵树一次 WAL 提交 ← **提交点** → 记录日志写提交标记」。树那一步失败
就是写失败:树按组原子回滚,prepare 的记录下次开库丢掉,调用方拿到错误。
原先记录日志先提交,所以树那一步失败留下的是 `ErrOutcomeUnknown`——一个
「一个存储里发生了、另一个里没发生」的状态,要把库围起来、下次开库重读整个
记录日志把树顶上去。

**开库时的 reconcile 整轮删掉了,它有害而不只是多余。** 树比归档新是故障后的
**正常**形态(提交在中间那个窗口里崩溃),而 reconcile 会把树推回归档说的样子
——那是丢掉一次已提交的写。这一条不是推理,是把顺序换过来之后测试直接抓到的。

**旧 generation 拒绝打开。** 静默 COW 重建同时是两件事:一次迁移,和一次
「读完整个记录日志来决定库里有什么」。保留前者、拒绝后者:开库报
`ErrUpgradeRequired` 并写明命令,重建是显式的 `memora upgrade --pages --yes`,
守护进程必须停。它是**唯一**还把记录日志当真相的地方,理由是老库必须能从那儿
走到这儿。

## 6.6 代价,逐条复核

裁定时写了三条,做完发现还有两条没写到。五条都在这里,不藏:

1. **失去「树坏了整个删掉重建」这层保险。** 如期。底换成了 §6 那条链;
2. **generation 升版语义要改。** 如期,而且比预计小——改成拒绝打开加一条显式
   命令,没有写就地迁移;
3. **不可逆。** 如期;
4. **归档可能落后一笔。**(裁定时没写到)group commit 与归档标记之间崩溃,
   那笔变更的 change 记录留在被丢弃的 prepare 段里,该 revision 取不到归属
   信息(History 退到 legacy 记录)。change index 有自己的 WAL,进不了同一个
   组提交,所以这个窗口是**结构性的**,不是能靠调顺序消掉的。已由
   `Authority.ArchiveError()` 报出来;
5. **跨文件的重复 ID 拒绝没了。**(裁定时没写到)那个检查**就是**被删掉的那张
   map,没有便宜版本。事务内的拒绝保留(记录都在手上);跨库的身份改由树的
   compare-and-set 管,它既是提交点又是原子的,而原先那个「读一下再拒绝」
   从来不是。

另外两件不算代价、但记下来免得下次当成回归:开库不再逐条验校验和
(`Verify()` 按需做,和 `page.Open` 只读一页是同一个形状);记录日志上**没有
索引了**,所以走回退路径读它就是走一遍文件——`no_scan` 那几道门相应改成断言
「不增长」而不是「零」,真正的读路径(走树)那道门仍然是零。

## 7. 明确不做

- **不引入 undo 日志**。「不需要 undo」靠的是 buffer pool 拒绝刷未提交页
  (`buffer.Pool.flush` 比 `durableLSN` 与页的 LSN),那是 WAL LSN 的性质,
  与记录文件的去留无关;
- **不动语义树(Route)的派生地位**。它本来就是导航覆盖层,这是对的;
- **不在本文处理向量检索**:整条链已于 2026-09-02 删除(`3ff6136`),
  偏差 14 随之关闭。重做时按第四条准则做成盘上索引。
