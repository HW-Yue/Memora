# 内部实现审查（2026-09-23）：长期使用的薄弱点

方法：Claude 先定"最贵 × 最没被覆盖"的三个子系统与各自需要的证据；然后**每个子系统一个审计员 +
一个对抗性复核员**（复核员逐条去代码里证伪：是不是把设计前提当缺陷、有没有漏看兜底机制）。
下面只收**复核判定为 real 或 partly** 的条目；**标 ✅ 的四条我自己又逐行核过代码**。

范围：派生层（召回单元 / vec0 / 修复队列）、daemon 生命周期与多进程并发、L2 结构变更与归档边界。
**不包含**已记录在库里的未关缺口（②③⑤⑥）——那些不必重报。

## 一、必须修的（按"出事最贵 × 现在最没被覆盖"）

### ✅ A1. 一张表只要历史上 `DROP_COLUMN` 过一次，就再也无法用计划改结构（critical，已复现）

- **代码**：`internal/schemachangeplan/build.go:41-51` 遍历 `table.Columns`（**不过滤归档列**）把每个
  列的形状塞进 `plan.ColumnGuards`；而 `validate.go:164-175` 拿 `catalog.LiveColumns(table.Columns)`
  （**过滤归档列**，`catalog/model.go:112-120`）与它 `reflect.DeepEqual` 比较 → 两者列数不等 →
  报 `revision_conflict: Column guards changed after planning`。
- **后果**：不是"刚 drop 的那一列"，而是"表里存在任何归档列"就永久锁死。`docs/decisions.md` 记录
  `me` 库四张表**已归档 23 列** → **真实库里的表基本全部中招**。唯一出路是 `UNARCHIVE COLUMN`，
  那等于把列变回活列，与 DROP 的意图相反。
- **已证**：审计员用纯内存实验复现（先 Build+Apply 一个 DROP，再对同表 Build 一个 RENAME →
  第二次 Apply 失败），零写入。
- **修法**：Build 的 guards 只取活列（与 Validate 同口径），或比对时两边都取活列 —— 一处口径统一，
  加一条"归档过列的表仍可改结构"的回归测试。

### ✅ A2. 写路径吞掉向量挂载错误：回执说成功、待办清单为空，只有 doctor 看得见（high）

- **代码**：`internal/sqlstore/rows.go:290` 与 `:437` 都是 `_ = t.attachVectorForRow(...)` ——
  返回值被丢弃。`acceptVector` 是"先真相后索引"：`embedding.go:92-99` 先写单元的
  `embedding/embedded_content_hash/model/dimensions`，`:102` 才 `storeVector`；后者失败时**真相列已写好**，
  而被吞掉的错误不会让事务回滚。
- **后果**：`SHOW PENDING VECTORS` 的谓词（`embedding.go:274-277`）全不成立 → 该行**不在待办里**；
  `unitVectorState` 只读真相列 → 判 `Ready=true`；`warnIfVectorDidNotLand` 见 Ready 即静默返回。
  **写回执与待办清单都在说谎**，只有 `doctor` 的 `vector_index_drift`（行级字节比对）看得见。
  对照：直接 `ACCEPT VECTOR` 的路径**会回滚**（`vecindex_test.go:616-660` 已断言）。
- **修法**：`attachVectorForRow` 的错误要么上抛（整笔回滚，与 ACCEPT 一致），要么至少进回执的 warning
  并把该单元算进待办。

### ✅ A3. `RESTORE` 回写行内容时不重建召回单元：旧文本仍然命中，新文本查不到（high）

- **代码**：`internal/sqlstore/rows.go:588-604` 的 restore 只做 `value.Values = ...` / `advance` /
  `writeRow` 就返回；**没有** `syncRecallUnit`，**也没有** `enqueueInboundRepairs`。
  对照普通写路径：`rows.go:284` 与 `:434` 都调 `syncRecallUnit`，`:401` 调 `enqueueInboundRepairs`。
  唯一写 `mem_recall_units.payload/content_hash` 的地方就是 `syncRecallUnit`（`recall.go:80-83`），
  而 restore 不改行状态时它也不会被别处触发。
- **后果**：`recall_vector.go:143` 用 `embeddedHash != contentHash` 判 stale，restore 后这一对 hash
  仍是同一份**旧值** → 判 ready；`brokenRecallUnits`（`recall.go:212-227`）只数"孤儿单元 / 活行无单元"，
  **不数 stale payload** → 静默。**关键词召回会命中已经不存在的文本，而现有文本查不到。**
- **修法**：restore 结尾补 `syncRecallUnit` + `enqueueInboundRepairs`（与普通路径一致），
  并加一条"restore 后新版本文本可召回、旧文本不再命中"的回归测试。

### ✅ A4. daemon 自锁：一个只 `BEGIN` 不 `COMMIT` 的请求会让**整个 daemon 失去响应**（high）

- **代码**：`executor/execute.go:136-144` 的 defer 无条件 `security.Record`；`audit.go:122→126-139→141-146`
  的 persist 走 `store.Begin(ctx, ReadWrite)`；`db.go:419-420` 第一件事是 `db.write.Lock()`。
  显式事务经 `api.go:318-322` 拿的是**同一把**锁，只有 commit/rollback 才 Unlock，
  而 `batch.go:187` 把事务放进 `session.active`、循环结束（`:251-262`）不回滚，只有 `Close`（`:276-291`）才回滚。
  CLI 默认不设 deadline（`cli.go:420` + `client.go:46-51`），而 `Lock` 不接 ctx。
- **后果**：第一个请求卡在 `db.write`，此后**所有**请求（含 ping / 只读 doctor）都卡在 Flush 的
  `service.mu`（`audit.go:130-131`）→ 整个实例失联，只有 SIGTERM 能让它解开。
- **修法**：审计落盘不能与业务写共用那把锁（独立连接/独立文件/先落内存再异步），或至少在事务
  打开时跳过 Flush；并给 CLI 请求加默认 deadline。

### A5. `engine_protocol` 不匹配只在**客户端**、且**执行之后**才拒绝（high）

- `ipc/protocol.go:30-37` 的 Request 根本没有 protocol 字段；`server.go:83-90` 只查 framing 的 version；
  引擎协议只在客户端拿到响应后比较（`client.go:81-87`）——**此时写已经提交**，客户端把结果整个丢弃。
  `ensureDaemon`（`cli.go:129-136`）只看 `state.Running`，从不比对协议。
- **后果**：换二进制后旧 daemon 仍在跑时，新 CLI 的写**真的落库**，还跳过向量排干（`cli.go:434-438`）。
- **修法**：服务端在**执行前**校验协议版本并整笔拒绝。

### A6. 两个 L2 回执无条件 `verified: true`，`VerificationCode` 从不赋值（medium-high）

- `route_plan.go:36-39` 与 `schema_plan.go:25-28` 都在 `db.update` **之前**就构造
  `Status: "committed", Verified: true`；`schemachangeplan/model.go:131` 的 `VerificationCode` 全仓无赋值。
  executor 原样透传，CLI 还用 `receipt.Verified` 决定退出码（`cli.go:359-361`）。
  对照：上层 `skillwrite/runner.go:61-72` 会真的读回验证并置 `Verified: false`。
- **后果**：直接消费 MSQL 的路径（MCP/SDK）会把"未经验证"当"已验证"。
- **修法**：回执的 verified 由提交后的读回计算，或干脆不要这个字段。

### A7. `REPAIR LINKS` 把**任何** readRow 错误当成"对端已消失"→ 静默删链接 + 无条件删队列条目（medium-high）

- `links.go:471-474` holder 读取任意错误都 `return false, nil`；`:483-487` counterpart 的任意错误被当成
  "The counterpart is gone" 走 `dropHolderLink`（`:626-642` 会**真实改写持有方那一行**并 appendHistory）。
  `readRow` 的错误不止 `ErrNoRows`：`db.go:512-520` 对非法 JSON 返回 `internal_error: stored value is corrupt`。
  队列删除是无条件的：`:442-451` 不论 applied 与否都在同一轮 `DELETE FROM mem_repairs`。
- **后果**：对端 JSON 损坏 → 一条合法链接被删除、队列条目消失、回执记 discarded、`broken_links` 回到 0。
  **数据丢失且无痕。**
- **修法**：区分 `ErrNoRows`（真消失）与损坏（保留队列 + 报错）。

## 二、真实的次级条目

- **B1（partly）**：`MembershipMoves` 执行时绕过 `advance/writeRow/appendHistory`（`route_plan.go:211-249`
  裸 `UPDATE ... SET route_leaf_ids`）→ 叶子间搬迁**不推进 revision/updated_at/commit_sequence、
  不写 history、不写行的 mem_changes**，计划里的 `MembershipMove.Revision` 是个**死字段**（从无校验）。
  执行期有叶子反向校验兜底，所以不是"旧计划能通过"，而是**挂载变更在审计面上隐形**。
- **B2（partly）**：`APPLY ROUTE MUTATION` 的第二道门（`routemutationplan/validate.go:74-81`）**不查环**，
  执行期 `checkTreeShape`（`route_plan.go:253-301`）也不查 kind、不查环；一份自洽的手写计划能把**环**落盘。
  之后 `recall_read.go:99-113` 与 `archive.go:23-46` 的父链遍历**没有 hop 保护** → RECALL/DELETE 死循环，
  而 `doctor` 只报 healthy。（叶作父那条被执行期挡住，落不了盘。）
- **B3（partly）**：位置解析失败被静默吞掉——`recall_read.go:77-80`、`recall_vector.go:96-99` 直接 `continue`，
  `query.go:415` 对 `node.Path == ""` 也 `continue`，而 `:179` 无条件把 `route_paths` 设成空数组。
  触发条件是**树已损坏**（例如 B2 的环），所以它是"损坏被掩盖"，不是长期使用会自己产生的缺陷。
- **B4（real）**：批内解析失败是否回滚，取决于首个词是否在 `mutationKind`（`batch.go:138-155` 与 `:429-437`；
  `parser/batch_items.go:104-112` 只把首词大写）。`REPAIR/ACCEPT/REKEY/ALTER` 四类**不在**该表里，
  于是残缺语句后面同一请求里的 `COMMIT` 会正常提交前面的写，回执同时显示"解析失败"与"COMMIT 成功"，
  重试会重复应用。
- **B5（real）**：`REPAIR RECALL UNITS` 对"live 行但叶子数 ≠ 1"**永不收敛**：`recall.go:311-314` 无条件
  返回 true，`syncRecallUnit`（`recall.go:81-83`）对这类行只删不建，而应用循环 `:287-296` 仍
  `rebuilt++`、`remaining` 不涨 → 每轮 rebuilt=1/remaining=0，`doctor.broken_recall_units` 不降，
  与 `recall_repair_test.go:72-79`"收敛后的一轮必须什么都不做"的断言直接冲突。
- **B6（real）**：`instance destroy` 把 `Inspect` 的错误当成"没在运行"（`instance.go:59-66`，
  `inspectErr == nil && state.Running` 不成立也照样 `RemoveAll`），且 `RemoveAll` **不持租约**
  （`AcquireMaintenance` 全仓零调用）→ 可能在别人正写的时候删掉实例目录。
- **B7（real）**：`internal/daemon` **920 行、零测试**，且全仓没有任何 `_test.go` 引用它
  （不只是包内没测，集成层也没测）。三条最该先补证据的不变量：Inspect 读操作却删 PID
  （`lifecycle.go:110`）、版本偏移"先执行后拒绝"（见 A5）、断连回滚路径。

## 三、查过但**不是**问题的（免得下次重复怀疑）

- `routetrace 292/0`、`nativeconfig 158/0`、`store 38/0` 零测试**不必紧张**：诊断输出与薄封装，
  坏了会在上层立刻显形，不会静默污染数据。
- `vec0` 宽度不符（`vecindex.go:141-151` 的就绪判定只信注册行 + 表名存在）：**doctor 的行级字节比对
  （`vecindex.go:261-285`）能看见**，原审计结论被对抗性复核修正——真正残留的只是"没有任何单元持有真相
  字节时，空且宽度错误的索引对 doctor 报 drift=0"。
- 归档/真删的边界：删 history、归档段不含 `aliases`/`synopsis`、`revision` 等字段**是文档写明的设计**
  （`docs/product/row-delete-archive.md`），且归档 INSERT 与真删在**同一事务**里，中断不会留半状态。
- rekey "单行道"：向量是派生数据（只用于定位、从不产出事实），释放后重嵌就是恢复路径；
  旧身份也能用带旧目标的 `REKEY` 写回。**是设计，不是缺陷。**
- 存储层没有实例锁（只有 daemon 的 flock）：今天没有可达的非测试路径，且 WAL + busy_timeout 保证
  不会页级损坏——真正被破坏的是逻辑单写者不变量，与已记录的缺口⑤重叠。

### 剩余项的设计决定（已经定好，别再重新推导）

**A6 · 回执的 `verified` 必须来自提交后的读回**
- 两处构造点：`internal/sqlstore/route_plan.go:36-39`、`internal/sqlstore/schema_plan.go:25-28`（都在 `db.update`
  **之前**写死 `Verified: true`）；`schemachangeplan.VerificationCode`（`model.go:131`）全仓无赋值。
- 做法：`db.update` 提交之后，用一次**只读 view** 读回并比对**计划自己声明的目标**（不要重写 applier 的逻辑，
  那正是 B4 的教训）：
  - SCHEMA：逐条 `plan.Actions` 校验后置条件 —— `ADD/RENAME/ALTER` 的 `After.ColumnID` 必须是**活列且形状等于
    `After`**；`DROP` 的 `Before.ColumnID` 必须**不再是活列**。
  - ROUTE：逐条 `plan.Creates` 节点必须**存在且 name/kind/purpose/parent 与计划一致**；`plan.Deletes` 的节点必须
    不可见（deprecated/已删）。
  - `VerificationCode` 填**读回形状的摘要**（必须非常量；或删掉该字段，二选一并在 decisions 里写理由）。
  - 不一致时：`Verified=false` **并带可诊断信息**（回执随返回值一起给，同时返回错误说明差在哪——
    "只置 false 不吭声"是不可接受的）。
  - CLI 的退出码继续跟 `receipt.Verified` 走（`internal/cli/cli.go:359-361`），executor 需要把新字段透传。
- RED 建议：端到端断言 `VerificationCode != ""`（改之前恒空）+ 对"读回校验函数"直接喂一个不一致的状态做单测
  （因为提交后无法在测试里插进"提交与校验之间"的篡改，除非加测试缝——加缝要在报告里说明）。

**B5 · `REPAIR RECALL UNITS` 对"live 行但叶子数 ≠ 1"必须收敛**
- `recall.go:311-314` 无条件 `unitNeedsRebuild=true`，`syncRecallUnit`（`:81-83`）对这类行只删不建，
  而应用循环 `:287-296` 仍 `rebuilt++`、`remaining` 不涨 → 与 `recall_repair_test.go:72-79` 冲突。
- 修法：这类行**不是"已重建"**，而是**被挡住**——要么计入一个新的 `blocked`（回执里能看出来是哪条行、为什么），
  要么把它算成 `remaining` 递减的"无法修复"并如实报；**关键是第二轮必须与第一轮不同**（收敛或明确 blocked），
  不能每轮都 `rebuilt=1/remaining=0`。

**B2+B3 · 环与坏路径的可观测面（一块做）**
- `routemutationplan/validate.go:74-81` 的第二道门**不查环**；执行期 `checkTreeShape`（`route_plan.go:253-301`）
  也不查 kind/环 → 自洽手写计划能把环落盘。之后 `recall_read.go:99-113` 与 `archive.go:23-46` 的父链遍历
  **无 hop 保护**（`withPath` 有 64 跳上限，唯独这两处没有）→ RECALL/DELETE 死循环，而 doctor 报 healthy。
- 修法：① Validate 补环检测（复用 `build.go:345-347` 的 `descendant` 或等价判定）；② 那两处父链遍历加
  **同样的 hop 上限**并**不再静默 `continue`**（`recall_read.go:77-80`、`recall_vector.go:96-99`、
  `query.go:415`、`:179` 的 `route_paths` 空数组）——**B3 不单开分支**：单独"补错误处理"只是把静默换成噪音，
  它必须和环防护一起做，成为"树坏了能被看见"的那一面。

**B1 · 叶子间搬迁要像别的写一样落账**
- `route_plan.go:211-249` 的 `moveMembership` 是裸 `UPDATE ... SET route_leaf_ids`：不 `advance`、不
  `writeRow`、不 `appendHistory`、不 `rowChange` → revision/updated_at/commit_sequence 不动、审计面隐形。
- 修法：改走正常行写的路径（`advance` → `writeRow` → `appendHistory` → `rowChange`），让
  `receipt.MembershipRevisions` 真的有对应。**`MembershipMove.Revision` 是死字段**：删掉它，或标注为
  informational——**不要**给它补一个没人写的校验。

**B6 · `instance destroy` 必须 fail-closed**
- `instance.go:59-66` 把 `Inspect` 的错误当成"没在运行"（`inspectErr == nil && state.Running` 不成立也照样
  `RemoveAll`），且 `RemoveAll` 不持租约。修法：Inspect 出错就**拒绝删除**并报出原因；

## 五、2026-09-25 新增：建第一个「配置库」时撞到的

背景：按 Skill 走了一遍完整建库流程（建库 `setup` → 建表 `models` → 建根 → 5 个 `mutate` 写行 →
排干向量 → 回读验证）。下面四条是过程中暴露出来的，最后一条是**查过但不是问题**的。

### C1. `write.md` 教错了「这张表有没有根」的检查方式（Skill 文本 bug，必修）

原文（`references/write.md`「Bootstrap a Router on a Table that has none」）：

> 1. Confirm the Table really has no root yet — **an empty rows array means none**.

**错。** `SHOW ROUTES … AT ROOT` 列的是根**下面的子节点**，不返回根自己：根刚建好、还没挂任何东西时，
它返回的同样是空数组。实测：`CREATE ROUTE ROOT` 第一次就成功了，我照这句话复查看到 0 行，以为没成，
再跑一次才报 `table "models" already has a route root`。

**后果**：照 Skill 做会重复建根，第二次失败；更坏的情况是有人据此判定"没有根"，转去走别的分支。
**修法**：把那句话改成"空数组只说明没有子节点；判断有没有根看建根那一步的返回，重复建根会报
`already has a route root`"，或者给一个能真正读出根的命令。

### C2. `memora mutate` 不排干向量，而 `write.md` 让你优先用 `mutate`（路径冲突）

- `recall-and-vectors.md`：配了 provider 的宿主，**`memora exec` 会替你排干**（写提交后问缺哪些单元、
  嵌入、交回）。
- `write.md`：**"Send the write through `memora mutate` when you can."**
- 实现（`internal/cli/cli.go`）：排干只在 `command == "exec" && len(statements) == 1` 时触发，
  **`mutate` 那条路径没有**。

**后果**：按 Skill 推荐的方式写行，向量永远是缺的——写全成功，`SHOW PENDING VECTORS` 里堆着，
直到有人手工排。这次 5 行就是手工排的（5 个单元，`embed_query.py` + 一批 `ACCEPT VECTOR`）。
**修法二选一**：让 `mutate` 也调 `drainAfterWrite`；或在 `write.md` 里明确写「`mutate` 之后必须自己排干」。
前者更对——否则"推荐路径"和"自动排干"永远不重合。

### C3. 写操作把非 JSON 提示打到 stderr，宿主合流就会炸（**不是引擎缺陷**）

现象：`memora exec … 2>&1 | python3 -c 'json.load(...)'` 报
`JSONDecodeError: Extra data: line 2 column 1 (char 1102)`——信封（1 行，1102 字符）后面跟了第二行。

**原因是宿主自己**：写操作会往 stderr 打非 JSON 提示，Skill 的约束里明写
"a host that parses stdout as JSON must **never** merge stderr into that stream"，我用了 `2>&1`。
`SKILL.md` 也早写了"writes also print non-JSON notes to stderr"。

**环境事实（值得记，免得下次又踩）**：本机 DSH 会话的环境里有
`MEMORA_EMBEDDING_MODEL/BASE_URL/DIMENSIONS` 三个变量，**缺 `MEMORA_EMBEDDING_API_KEY`**——
即"部分配置的 provider"，正是 Skill 说的那个常见 case。所以这个会话里**每次单语句 `exec` 写都会打 note**；
`query`（读）不会。**规则**：解析 stdout 就永远不要把 stderr 合进去；要看提示就分开重定向。

### C4. 在 Skill 树里跑 `python3 -m py_compile` 会制造"假 drift"（流程陷阱）

`py_compile` 会在 `scripts/` 下留 `__pycache__/`，而 `internal/devgate` 比的是**整棵 Skill 树**，
于是 adapters 全都报 `missing scripts/__pycache__/jev_tree.cpython-314.pyc`——看起来像 Skill 分叉，
其实是编译缓存。**规则**：改完 Skill 的 python 脚本要检查语法就用 `python3 -m py_compile` 之后
`find skills -name __pycache__ -exec rm -rf {} +`，或者用 `python3 -c "import ast,pathlib; ast.parse(...)"`。
