# 实测缺陷报告：以真实 agent 身份用 skill + 引擎

状态：**进行中**（2026-09-21 起）。被测对象：`skills/memora/`（引擎仓库内的规范技能）、
发行仓库 `~/Developer/memora-skill`、本机实际安装的三处 `~/.agents|.claude|.codex/skills/memora`。

方法：不读源码先当用户——照 SKILL.md 写什么就做什么，卡住就记一条。

## D1 · 本机安装的 skill 落后 M4–M7 全部读面（严重）

**现象**：`~/.agents/skills/memora`、`~/.claude/skills/memora`、`~/.codex/skills/memora`
三处安装的 `SKILL.md` 是同一份 **471 行**的旧版本（文件时间 2026-09-20 23:31），
而引擎仓库的规范版本是 **618 行**。关键能力在已装版本里**一次都没出现**：

| 关键词 | 已装版本 | 引擎版本 |
|---|---|---|
| `RECALL` | 0 | 5 |
| `ACCEPT VECTOR` | 0 | 1 |
| `SHOW PENDING VECTORS` | 0 | 2 |
| `SHOW ARCHIVE` | 0 | 2 |
| `REPAIR LINKS` | 0 | 1 |
| `vectors_not_ready` | 0 | 1 |
| `embedding` | 0 | 9 |

**影响**：真 agent 读这份 skill，就不知道召回、归档读面、链接懒修复、向量提交与排空的存在，
只会用 M3 之前的写法——**功能实现了但用户用不到**。

**修**：把规范版本同步到三处安装位（保留备份），并让"落后"可被检测（见 D3 的修法）。

## D2 · 发行仓库 `memora-skill` 仍在教已被删除的命令（严重）

**现象**：`~/Developer/memora-skill` 的 `SKILL.md` 是 **762 行**的旧内核版本，正文里写着
`memora assimilate`、`capture`、`decide`、`feedback`、`maintain`、`reflect`、`upgrade`，
以及 `doctor repair` 与 `memora upgrade --plan/--apply`。这些命令在现役 CLI 里**已经不存在**
（引擎 devgate 的删除清单里明确禁止这些字符串再出现在技能文档里）。

**影响**：照这份文档操作会**每一步都失败**。三份副本各说各话本身就是缺陷。

**修**：以引擎仓库 `skills/memora/` 为唯一真源，覆盖发行仓库内容并提交。

## D1/D2 的修法已落地

- 三处实盘安装位同步到规范版（备份留在 `/tmp/skill-backup-20260921-180938/`）；
- 发行仓库同步并提交（`faefd30` + 后续一次）；
- **新增 `scripts/sync-skill.sh`**：一条命令管整条链，`--check` 只报告不改动。它就是 D4 的修法。

## D5 · 适配器之间的 `openai.yaml` 早就分叉了（中，由 D4 的修法当场抓到）

**现象**：`scripts/sync-skill.sh --check` 一跑就报出——codex 适配器的 `agents/openai.yaml`
与规范版不同，claude-code 适配器**根本没有这个文件**，而且它的 `manifest.json` 里也没登记。

**影响**：两个适配器携带的文件集不同，而门禁的共享清单恰好不含这个文件，所以谁都发现不了。

**修**：同步文件、把条目补进 claude-code 的 `manifest.json`（路径前缀跟着各自 adapter 走）、
`--check` 现在为零漂移。

## D3 · `check.sh` 指向一个不存在的 Release（中）

**现象**：`skills/memora/scripts/check.sh` 在没装 CLI 时输出
`"release_url": "https://github.com/HW-Yue/Memora/releases/latest"`，
但引擎仓库的 `.github/workflows/release.yml` 是个**拒绝发布**的桩（打 `v*` tag 会明确失败）。

**影响**：agent 会让用户去一个**没有产物的 release 页**下载；指导是错的。

**修**（已落地）：改成输出 `install_url` 指向 README 的源码安装段，并注释写明"等发布链路
落地后换成真实 Release，否则用户会被指向 404"。

## D4 · 没有任何"已装 skill 是否落后"的检测（中）

**现象**：三份副本分叉了却没人知道。引擎仓库的 devgate 只保证
`skills/memora/*` 与两个 adapter 副本 + manifest 摘要一致，管不到用户机器上的安装位。

**修**（已落地）：新增 `scripts/sync-skill.sh`，一条命令管整条链——

```sh
scripts/sync-skill.sh --check                      # 只报告漂移（适配器 + 可选目标目录）
scripts/sync-skill.sh                              # 同步仓库内的适配器副本
scripts/sync-skill.sh --install ~/.agents/skills/memora
scripts/sync-skill.sh --publish ~/Developer/memora-skill/memora
```

`--check` 是入口：三份副本分叉这件事因此**可查**，而不是靠人记得重装。

## 实测一：文档里的语句逐条走（25 条）

方法：新建实例，照 SKILL.md 的建模步骤建库/表/根，然后把文档里出现的**每一条**语句
（发现 4 条、建模与写入 4 条、导航 4 条、召回 5 条、归档/修复/配置/提案 6 条 + 前面几条）
用真实参数跑一遍。

**结果：23 条 OK，2 条失败，都不是代码缺陷**——那两条是文档里的**提案示例**，示例里的
`expected_table_revision: 4`、`column_id: "col_title"`、`route_source` 是**占位值**，照抄会得到
`revision_conflict` 与 `not_found`（语义错误，不是语法错误），说明解析与校验是对的。

单独验过的三处文档声明也都成立：

| 文档说 | 实测 |
|---|---|
| `CREATE ROUTE` 是 L2，L1 会被拒 | `permission_denied: ... do not permit risk level L2`（ROOT 与 UNDER 都是） |
| `memora parse` 存在 | CLI help 里是 `parse  Parse an MSQL request through the local daemon` |
| 新行必须挂一个叶子 | `constraint_violation: a live Row needs exactly one leaf, got 0: attach an empty leaf, or create one first` |
| `CREATE ROUTE ... SYNOPSIS :synopsis` 可选形式 | 接受 |

## D7 · 提案示例的占位值看起来像真值（低）

**现象**：两个 `PLAN ... USING :proposal` 示例里的 revision／id／route_id 用的是具体值
（`expected_table_revision: 4`、`col_title`、`route_source`），照抄会得到 `revision_conflict`
或 `not_found`。

**影响**：agent 可能以为是引擎的问题，而不是"这些值要换成你自己的"。**修**：在示例旁注明。

## D8 · 文档没说清挂载的两种写法（低，已修）

**现象**：正文写"pass that id in the Row write's `route_leaf_ids`"，而紧接着的 **INSERT 完整
示例**用的是 `route_path`；UPDATE 示例用的是 `route_leaf_ids`。读者会以为 INSERT 只能用后者。

**修**：改成明确列出两种写法、各自何时用，并点明**两者都在 `mutation` 里、都不在顶层**——
这一层深度是实测中最容易写错的地方（我自己在写测试驱动时连错三次，每次都被严格解码挡下）。

## 实测二：第四条路 jev 的完整 journey

不是只测脚本，而是走完整条路：

```
① 内核给出第一层：工作(branch) / 技术(branch) / 生活(branch)   ← SHOW ROUTES AT ROOT
② 交给 jev（只送 name + purpose，不送 route_id）
   jev 选了: 技术（confidence 0.98，model jev-1.13.0）
③ 用选中的名字换回内核的 route_id → SHOW ROUTES UNDER → 存储引擎
④ OPEN ROUTE → SELECT → "页格式与崩溃恢复交给 SQLite"
```

置信度那一栏也实测过两端：意图明确 → 0.98–1.0；故意含糊（"嗯……那个东西"）→ 0.58。
SKILL.md 因此写明低置信度当"问用户或自己决定"。

## D9 · agent 实际用的二进制早于 M4–M7（严重）

**现象**：`check.sh` 报 `ready`，但 `~/.local/bin/memora` 是 **9-13 20:12** 构建的
（`version 0.2.0-sqlite / commit fe4cfe7`），而主线是 `cde5bff`。它不是"看起来旧"，是真的旧：

- 它的 `query` 在**本机**就把 `RECALL` 拒了（那张硬编码只读白名单正是 F2/F4 修掉的东西）：
  `query only accepts SHOW, DESCRIBE, SELECT, OPEN ROUTE, or read-only PLAN statements`；
- 用它起的 daemon **解析不了**新语句：`SHOW PENDING VECTORS … -> parse_error`。

也就是说：**技能修好了，二进制还是旧的，agent 照样用不了召回。**

**根因之一**：CLI 是薄客户端（语句转发给 daemon），所以版本错配表现为
"新 CLI + 旧 daemon → 解析失败" 或 "旧 CLI → 本机就拒绝"。而 `check.sh` 只报 CLI 自己的版本，
**没有任何地方能发现 CLI 与 daemon 的版本差**。

**修（已落地）**：备份旧二进制到 `~/.local/bin/memora.bak-20260921-181641`，装入当前主线，
并按 SKILL.md 的命令逐条实测通过——`RECALL MATCH '字典序'` → `root → MSQL与导航 → 召回`；
`SHOW PENDING VECTORS` → 0 个未就绪；`RECALL NEAREST`（真算一个查询向量）→ 命中同一条。

**建议（未做）**：`check.sh` 除了报 CLI 版本，还应问一次**运行中的 daemon** 的版本并在不一致时
报 `skewed`——否则同一个"版本错配"会在下次升级时原样重演。

## D10 · 安装器没有用法提示（低，已修）

**现象**：`install.sh --help` → `unknown option --help`。安装器的选项（装哪个版本、装到哪、
要不要初始化实例）都不可猜，出错时只得到一句"unknown option"，读者无从下手。

**修**：加 `usage()` 与 `-h|--help`，列出全部选项，并写明源码构建需要 cgo 与 `sqlite_fts5` 标签。

## D11 · 普通 `go build` 出来的版本是 `dev/unknown`（低，建议）

**现象**：用 `go build` 直接构建，`memora version --json` 是
`{"version":"dev","commit":"unknown","built_at":"unknown"}`；而 `install.sh` 会带
`-ldflags "-X main.version=… -X main.commit=source -X main.builtAt=source"`。

**影响**：`check.sh` 与"哪个二进制更新"这类判断在自建二进制上失去依据（D9 因此更难被发现）。
**建议**：把 `install.sh` 明确为发布/安装路径，或在文档里给出等价的 ldflags。

| # | 事项 | 状态 |

| ① | CLI 去掉硬编码只读白名单，只读判定移到 daemon | **✓ 本提交** |
| ② | daemon 未运行时 CLI 幂等自动起 | **✓ 本提交** |
| ③ | `go build` 的版本身份（build info） | **✓ 本提交** |
| ④ | 握手 + `check.sh` 报两者 | **✓ 本提交** |
| ⑤ | `install.sh` 无 release 时诚实降级 | 待做 |
| ⑥ | SQLite schema 版本守卫 | **✓ 本提交** |
| ⑦ | 测试实例 teardown | **✓ 本提交** |
| ⑧ | 发布链路 | **✓ 本提交**（并已手工发出 v0.2.0） |
| ⑨ | Linux 进 CI | 待做 |

①的实测：`memora query` 发一条写语句 → daemon 请求级拒绝
`unsupported_statement: this transport is read-only: …`；同一条 `query` 发 `RECALL` → 正常作答
（旧 CLI 会在本机把它拒掉）。只读判定现在只有一处权威（daemon），客户端不再持有语句清单。

②的实测：无 daemon 时第一条 `query` → 自起并只打印一行
`memora: started the instance's daemon (pid N); it was not running`，结果正常返回；
第二条不再打印（幂等）；`daemon stop` 两次第二次说 `daemon is not running`，且之后**没有**
被重新拉起（`daemon` 子命令不在自动起范围内，所以不会递归）。SKILL.md 相应改写：agent 不必
自己先跑 `daemon start`。

③的实测：普通 `go build` →
`{"version":"dev","commit":"7e9969ac1dfc…-dirty","built_at":"2026-09-21T13:02:09Z"}`
（`-dirty` 是因为当时工作树有未提交改动——**两个 commit 相同但工作树不同的构建不是同一个二进制**，
所以说出来是对的）；带 `-ldflags` 的安装/发布路径仍然覆盖成它给的值。这是 ④ 握手的前置：
两边都报 `dev/unknown` 时，握手会判"一致"，错配检测在最常见的本地构建下恒假阴性。

④握手的实测（两个真二进制，双向都跑过）：

- **新 CLI + 旧 daemon**（旧 = 改动前的 `53e1cb4`）：旧 daemon 不盖字段 → 解码为 0 →
  ```
  memora: query MSQL: the daemon speaks engine protocol 0, this client speaks 1
  memora: this client and this instance's daemon are different builds, so the client cannot know the daemon's syntax.
    restart the daemon with the binary you are running:
      memora daemon stop --data-dir "…" && memora daemon start --data-dir "…"
  ```
  退出码 1。
- **旧 CLI + 新 daemon**：旧 CLI **照常拿到结果**——它根本没有这段代码，所以**旧客户端无法被追溯
  修复**。这不是缺陷，而是为什么必须补上 `check.sh` 报两边版本：那是唯一能发现"CLI 自己旧"的地方。

设计要点：协议号放在 **IPC 响应**里（`response.server_protocol`），不是语句信封里——于是
**每一个响应**都带它（msql／doctor／ping／trace），客户端只在**一处**校验，新增 RPC 也不可能忘记。
字段 `omitempty`：旧 daemon 不发 → 0 → **判为 skew，而不是一致**。

④全部落地的实测：

- **新 CLI + 旧 daemon**：`daemon status --json` →
  `{"cli":{…},"daemon":{…},"skewed":false|true}`，旧 daemon 时是
  `{"daemon_error":"the daemon speaks engine protocol 0, this client speaks 1","skewed":true}`。
- **`check.sh`** 现在同时报 CLI 与实例：`ready` / `skewed`（实例里 `"skewed":true`）/
  `unknown`（旧 CLI 根本答不了这个问题——**这本身就是结论**，不是失败；以前它会报假的 `ready`）。

关键取舍：身份**只从"谁在应答"取**（`build` 方法问运行中的 daemon），实例目录里的任何版本记录
都不作数——目录比进程活得久，重启、原地换二进制之后它就陈了。

## D12 · "最新 release" 是我们这条线 253 个提交之前的构建（严重，且推翻 ⑤ 的前提）

**现象**：`install.sh` 默认路径**是通的**——它解析到 `v0.1.2`、校验 checksum、装上了。但

```
ae237c4  2026-08-17  feat(skill): installer defaults to the latest GitHub release
落后主线条数: 253
```

`v0.1.2` 是**我们这条线的祖先**（不是另一条线），只是极旧。所以"安装脚本指向一个不存在的
release"这个前提**是错的**：它指向的是一个**真实但落后 253 个提交**的构建。真实危害是
**静默变旧**——安装成功、`version` 看着正常，功能却停在两个月前（这正是 D9 那台 8-13 二进制的
来源）。

**修（本提交）**：保留"无 release 时降级到检出构建"的诚实逻辑（对未来缺 tag 的情况仍然正确），
并让**从检出里运行时优先构建检出**、把"没有已发布 release，改为从这里构建 + 代价"明确说出来。

## D13 · 旧二进制会照常"迁移"新实例（严重，⑥ 的现场证据）

**现象**：上面那次安装顺带用 `v0.1.2` 跑了 `init` + `doctor`，**目标是你真实的实例**。事后看
实例里多了一批**旧内核的表**：`mem_postings`、`mem_vectors`、`mem_vector_items`、`mem_links`
——它们不是当前主线创建的。

**影响**：我们的表没被破坏（doctor 除了下述积压都健康），但这**正面证明了** Claude 的警告：
一个旧二进制面对更新的实例**不会报错，会按自己的 schema 去写**。方向反过来（新 daemon 迁移过、
再回滚到旧 daemon）就可能**误读或写坏**。⑥（schema 版本守卫）因此从"建议"升为**必须**。

## D14 · M7 之前的活行没有召回单元，且**没有重建入口**（严重）

**现象**：实例 `doctor` 报 `broken_recall_units: 74`，而 `mem_recall_units` 只有 2 条。逐项查过：
74 = **M7 之前写入的活行没有单元**（不是单元指向了不存在的表，那种是 0）。这些行写入时，
"一叶一单元"这个派生层还不存在。

**影响**：**关键词召回对这些行完全无感知**——`RECALL ... MATCH` 命不中它们，而 `RECALL` 的通知
只覆盖"向量未就绪"，**不覆盖"这个行根本没有单元"**。也就是说：老用户升级到 M7 之后，
召回会静默漏掉他几乎全部的记忆，而 `doctor` 是唯一说出这件事的地方。而且**没有任何入口能重建
单元**：行只有在被写入时才会得到单元，`REPAIR VECTOR INDEX` 修的是向量索引，不是单元。

**建议**：把"重建召回单元"做成一条有界、可分页、可重复的一等语句（与 `REPAIR VECTOR INDEX`
同族），并把"单元缺失"并入 `RECALL` 的通知——否则升级即静默失效。

## D15 · 安装器会去动"默认实例"（严重，D13 的机制）

**现象**：`install.sh --install-dir /tmp/install-test2` 这种"我只想装个二进制到临时目录"的调用，
**依然对默认实例跑了 `init` 与 `doctor`**——输出里就是你会话里那个实例的 ID。不给 `--data-dir`
时它走 `else` 分支，直接 `init` / `daemon start` / `doctor` 默认实例。

**影响**：这就是 D13 的机制——装一个**候选或更旧的二进制**，会顺手把用户的**真实记忆**交给它
去 `init`/迁移。用户以为自己只是装了个工具。安装器**不该在没有被告知是哪个实例时触碰任何实例**。

**修（本提交）**：不给 `--data-dir` 就只装二进制并打印"如何创建一个实例"，一个字节都不碰；
给了才 `init` + `doctor` 那一个。实测两条路径：不给 → `installed into …; no instance was touched.`；
给了临时目录 → 只初始化那个临时实例。

⑥的实测：`PRAGMA user_version` 现在记录文件形状（`fileSchemaVersion = 1`）。

- **更新的实例被拒**：把标记设成 `+7` 再打开 → 报
  `this instance was written by a newer Memera (file schema 8, this binary understands 1): upgrade the
  binary instead of opening it with this one`，且**拒绝时不会把标记改回自己的版本**（测试断言了）。
- **升级路径**：标记为 0 的旧实例（你本机那个就是）→ 打开、迁移、盖上 1；再打开是无事发生。
- 刷新判据写在注释里：**加列不需要 bump**（加列迁移自己处理），只有当旧二进制**已经不能正确读**
  这个文件时才 +1。
- 诚实说明它的边界：守卫只能保护**有它的二进制**——已经发布出去的旧版本教不会。它买到的是
  "从现在起每一个二进制都会拒绝退化"，而不是"修复历史"。

## ⑥b · 重建召回单元（D14 的修法）

新增一等语句 `REPAIR RECALL UNITS IN DATABASE <db> LIMIT <n>` → `{rebuilt, dropped, remaining}`：

- **补上没有单元的行**（M7 之前的活行）、**删掉行已消失的孤儿单元**（它指向一个不存在的位置，
  比"找不到"更坏）、**刷新文本已变的载荷**；三者的判据与 `doctor` 的 `broken_recall_units` 同源。
- **不修改任何行、不重算任何向量**：它只重建派生层，复用单元的唯一写入口 `syncRecallUnit`。
- 有界、可重复（与 `REPAIR VECTOR INDEX` 同族）：`LIMIT` 受 `max_affected_rows` 约束，跑到
  `remaining` 为 0 为止。

实测（合成的"单元从未存在过"状态）：3 行无单元 → 关键词召回 0 命中、doctor 报 3 →
一次 pass → `{rebuilt:3, dropped:0, remaining:0}`、doctor 归 0、召回重新命中；
孤儿单元（把 `row_id` 改成不存在的值）→ `{dropped:1, rebuilt:1}` → doctor 归 0 → 再跑是
`{0,0,0}`；语句面同样有测试（含超预算的 `LIMIT` 被拒）。

### ⑥b 在真实实例上的结果

你本机那个实例（`~/Library/Application Support/Memora/instances/default`）：

```

REPAIR RECALL UNITS IN DATABASE memora → rebuilt=65  dropped=0 remaining=0
修之后： rows=76  broken_recall_units=0  vector_index_drift=0
```

修完立刻验证**旧的记忆能被召回了**（此前完全无感知）：

```

                                    root → 现行 → ADR-0003
```

（`me` 库那 9 行同样重建完成；我用 1 字查询试它时引擎按规则拒绝了 1–2 字查询——那是设计，
不是缺陷。）

⑦的实测：新增 `memora instance destroy --data-dir <绝对路径> --yes` —— **删目录**，不是不可逆的 DDL。

- **只有自称是实例的目录才会被删**（`instance.Read` 先验证 `instance.meta`），所以打字错误删不掉
  别的东西；相对路径、缺 `--yes`、缺 `--data-dir`、写错动作，全部拒绝。
- 删之前先停该实例的 daemon（graceful；停不下来就不删）。
- **语言里没有 DROP**，所以"建了个测试库想删掉"只能走这条命令——这也回答了 D14 之后那个疑问：
  真正需要的是 teardown，不是不可逆的 `DROP DATABASE`。

测试两条：正常路径删掉目录并报告删了哪个实例；五种"不该成功"的输入全部拒绝，且**没有删掉任何
东西**（实例与普通目录都在）。

## D16 · 宿主排干一次要 64 个单元，而 provider 只收 10 个（严重）

**现场**：整库重建后 41 个单元全部没有向量。在本机（`~/.zshrc` 里的 `MEMORA_EMBEDDING_*`，
provider 是 DashScope 兼容模式、`text-embedding-v4`、1024 维）跑一次 `memora exec` 触发排干：

```text
embeddings: stopped after 0 vector(s): the embedding provider answered 400 Bad Request; the rest stay not-ready
embeddings: attached 9 vector(s)
```

`me`（9 个单元）一次排干；`memora`（32 个单元）**0 个**，而且每次重试都会再从队头取 64 个，
再失败一次。直接问 provider 拿到它的原话：

```text
batch=10  HTTP 200
batch=24  HTTP 400  "batch size is invalid, it should not be larger than 10.: input.contents"
```

**根因**：`internal/cli/embedding.go` 的 `drainBatch = 64` 是写死的，而 provider 的上限是 10。
后果不是"慢"，是**超过 10 个待办的库永远排不干**：重试永远从同一页开始、永远 400，
stderr 一行就过去了，`doctor` 只说 `units_without_vectors` 不为零。

**当场绕过**：按 provider 的批大小分批嵌入、逐个 `ACCEPT VECTOR`（`/tmp/drain-in-tens.py`），
32 个单元全部补上，`doctor` 变成 `units_without_vectors: 0`、`vector_index_drift: 0`。
两个库的 TOFU 身份都锁在 `text-embedding-v4` / 1024。

**建议的修法**（未开工）：宿主排干遇到 provider 拒绝时要能**退到更小的批**——
拿到 4xx 且批大于 1 就二分重试，只有单个输入仍失败才算这个单元排不了；再给一个
`MEMORA_EMBEDDING_BATCH`（默认取一个保守值）避免每次都先撞一次。判据：一个 32 个单元的库
在"每次最多 10 个"的 provider 下也能一次排干。

## D17 · `memora exec --input` 装不下"一批语句"的输入（中）

**现场**：`--input` 只解码**一个** `StatementInput` 对象（`internal/cli/cli.go`：`--input must be
one strict StatementInput JSON object`）。所以 Skill 里"一条语句一个单元，批量＝一批语句"这句，
用 CLI 实现不了——10 个 `ACCEPT VECTOR` 要么发 10 次 `exec`，要么走 MCP/SDK/Gateway
（Admin 的 `statements: [...]` 就是数组）。CLI 自己的排干能用批，是因为它直接调内部的
`ExecuteMSQL(ctx, dataDir, source, inputs []StatementInput, readOnly)`，没经过这个 flag。

**影响**：agent 按 Skill 的指引补向量时会退化成 N 次往返；也解释了为什么"批量"这条只在
内部与 Gateway 成立。

**建议的修法**（未开工）：允许 `--input` 接一个数组（或 `{"statements": [...]}`），
数量与解析出的语句数严格一致，行为与 Gateway 相同。
