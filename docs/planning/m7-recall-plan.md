# M7 召回：详细实施计划

状态：**方案**（2026-09-21 出，待授权）。产品形态见
[查询形态](../product/query-model.md) §6 与[检索路线](../query/retrieval-routes-jev.md)。
本文件只管**怎么拆、什么顺序、各自验收**；逐项工单仍以[执行计划](./execution-plan.md)为准。

## 目标与验收

**目标**：四条路里最先落地两条——关键词召回与向量召回，各自跑通一次**端到端闭环**：

> Agent 手里**没有路径** → `RECALL` 拿到候选语义路径 → （可选）逐层导航 → `SELECT` 回表取事实。

**召回的铁律**（已定，不重开）：只回答"命中项在语义树的哪个位置"。返回**逐段带 `route_id`
的完整路径** + `database`/`table` + 末端 `kind` + 命中 Row 时的 `object_id`。
**不返回**分数、距离、排名、理由、命中字段、正文。`limit` 必填有界；同一路径去重；
排序内部做、对外按路径字典序稳定输出；召回不代替调用方行动（不回表、不预取、不缓存）。

**不在 M7**：jev、Skill 编排、任何形式的分数或正文回传、PDF/图片/chunk 向量。

## 工程前置（已实测，不是假设）

- **FTS5 当前没编进来**（`no such module: fts5`）。加构建标签 `sqlite_fts5` 后
  `fts5` 与 `tokenize='trigram'` 都能建——已验证。
- **vec0 也没编进来**；`github.com/asg017/sqlite-vec-go-bindings` 可达，
  旧版本二进制曾带 v0.1.6（等于恢复一个曾经存在的能力）。
- 内容以中文为主：FTS5 默认分词对中文几乎无用，**`trigram` 是内置可用选项**。

## 三处岔路（已定，2026-09-21）

1. **可召回单元的粒度**（最大风险所在）：单元挂在**叶子（route_id）**上，一个叶子一个单元，
   文本载荷取该行 `ROLE summary` + `title`（无则第一个 TEXT 列）。理由：召回返回的正是
   **语义路径**，叶子是路径的末端、且一行恰好一叶（1:1 已强制），所以"单元 = 叶子"让路径天然唯一。
   branch 不进索引（它不挂行，命中它还得下钻，不属于召回要回答的问题）。
2. **向量谁产出**：**宿主侧算好交回**。但**缝要收窄**——调模型的那段**不进 `sdk/memora`**：
   让发布的 Go 客户端读 provider 环境变量并发 HTTP，等于 Memora 自己成了 provider 调用方，
   直接违反既有规则（Provider 属于宿主，base URL 与 key 绝不交给 Memora），而且宿主未必有模型。
   分工：
   - **Memora 侧只搬运**：① 有界列出待向量化单元（`route_id`／`row_id` + **确切文本载荷** +
     内容哈希 + 该单元要求的 `model`／`dimensions`）；② 有界、**幂等**地提交向量，校验维度、
     model 标签、以及哈希是否仍是当前文本（对不上即拒，说明文本又变了）；
   - **宿主侧**（`skills/memora/scripts/` 里的脚本，与 `install.sh`／`check.sh` 同处）读
     `MEMORA_EMBEDDING_*`、调 `POST {BASE_URL}/embeddings`（带 `model`／`input`／`dimensions`）、
     再把向量交回。
3. **可见性**：**词法同步（同事务）**，**向量异步（队列回填）**。理由：中文 trigram 成本可控，
   异步只会把"刚写就召不回"变成必现 bug；向量有外部模型，同步会把网络延迟塞进写事务。

### 向量的来源标记（换模型与改正文的安全网）

每个向量必须记 **`model` + `dimensions` + 文本内容哈希**。换模型或改了正文 → 旧向量作废、
单元回到队列。维度必须跟模型走：维度一变就是另一个索引（vec0 的维度是建表时定死的）。

### 本地模型（测试用，已确认）

用户已在 `~/.zshrc` 配好阿里云百炼 OpenAI 兼容模式：
`MEMORA_EMBEDDING_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1`、
`MEMORA_EMBEDDING_MODEL=text-embedding-v4`、`MEMORA_EMBEDDING_DIMENSIONS=1024`，
`MEMORA_EMBEDDING_API_KEY` 有值（**密钥不写进仓库、不进数据库、不进日志**）。

**硬约束：仓库测试不许碰网络**（既有约定）。因此 F5／F6／F7 的测试用**确定性的本地假向量器**；
阿里云这条真链路只在 skill 的**冒烟脚本**里手动跑，**绝不进 `ci.sh`**。

## 风险

1. **可召回单元的边界定错**（最大）：粒度或失效责任定错，两条通路一起返工。缓解——
   Feature 3 先只落表与维护，不接任何召回；用"哈希不变则不重算""结构变更即时失效"两条测试钉死。
2. **向量队列积压**：向量长期陈旧而对外不可见。缓解——`RECALL` 明确报"未就绪单元数"，
   不允许把"没向量"伪装成"没命中"。
3. **构建标签的渗透**：`sqlite_fts5` 一旦漏掉某个入口（vet/lint 的平台 sweep、release），
   就会出现"本地能跑、CI 或发布件不行"。缓解——Feature 1 把标签写进 `ci.sh` 与 workflow，
   并加模块可用性断言测试。
4. **`sqlite-vec` 是新的 C 依赖**：如果它在某个平台构建失败，Feature 6 会卡住。
   缓解——F1 的可用性测试同时断言 vec0；卡住时 Feature 5 的队列照常可用，只是 `RECALL` 报未就绪。

## 冒烟脚本要跑的闭环（手动，不进 CI）

## F6 之前必须先钉死的约束（2026-09-21 咨询）

前三条来自三件欠账复审，后六条是复审时挖出的、此前没人看见的风险。标**待定**的要产品
拍板，其余是技术结论。

**A. 信封构造即合法（做在 F6 新增输出之前）**
不变量必须绑在"信封这个值"上，而不是"序列化这个动作"上：缺必需字段（如列表页的
`snapshot`）的信封**构造不出来**，于是进程内路径（Skill 层、jev、将来的嵌入式消费者）
与生产路径**无法分叉**。测试里强制序列化 + 表驱动往返照做，但那是网不是墙——只堵第二条
路径、路径本身还在，等于踩中判据⑤。

**B. 模块缺席是运行期一等概念**（契约，**待定**）
vec0 缺席时报的不能是裸 SQL 语法错：Agent 自主建模的前提是它能**机读**地知道"这个二进制
没有向量路"。同时"四路都返回同一种语义路径"这条承诺在某路可缺席时带了条件分支，这该当
契约定，不该当 build flag 定。要定：vec0 与 `sqlite_fts5` 是联合标签还是两根正交标签、
CI 跑不跑矩阵、模块缺席时 `RECALL` 与能力发现面各自怎么答。

**C. 缺席模块时队列必须拒收**（与 B 同一个决定）
若 vec0 缺席而写入队列照收，就是攒一个**该二进制永远排不掉的派生状态**——判据②（派生状态
不可重建）当场响。缺席时必须在入口拒绝，而不是入队后无声积压。

**D. 向量真相落普通表，vec0 只是它的索引**（数据模型，**待定**）

  已核实（2026-09-21，sqlite-vec 官方文档）：vec0 的向量**不在另一个文件里**，而在同一库文件的
  **影子表**（`<表名>_vector_chunksNN.vector` BLOB、`_rowids`、`_chunks`）里；辅助列另有
  `_auxiliary`。所以 D 不是"要不要多一个文件"，而是**谁能读、谁拥有格式、丢了能不能自己重造**：
  影子表格式是扩展内部格式，官方标注为内部文档且未承诺稳定，普通 SQL 不能把它当真相读，
  跨版本、被 DROP 或损坏后都无法自行校验与修复。
例外边界"只在派生层"要物理成立，embedding 原文（blob + dim + model_id）必须作为**真相**
落普通表；否则 `mem_recall_units` 里只有叶子、没有向量，而 Memora 不发网络请求、不持 key，
"可从 `mem_recall_units` 重建"就变成"求宿主重算"。**不落真相表则 ADR-0011 的例外站不住。**

**E. `unit_no` 单调不复用**
叶子删除后整数不得被复用，且删除叶子时**同一事务**删掉对应 vec0 行。否则一条没清掉的旧
向量会在新单元下复活，把召回指到**错误的语义路径**——而召回不返回分数，这种错**无法从
输出察觉**。

**F. 删除/归档与向量索引的一致性**
DELETE 时向量行必须立刻消失，否则召回会把路径指进归档空间。归档／恢复的向量侧责任沿用
同一条分割线：**引擎归档、Agent 恢复**（引擎不替 Agent 重建向量）。

**G. 模型身份即索引身份**
同一 vec0 里混进不同宿主模型／维度的向量就是静默垃圾。要有 `model_id` + `dim` 的真相戳，
更换模型即索引失效——**这是向量路的 `snapshot`**，与归档页"视图身份"同一个思路。

**H. 确定性从性质升格为不变量**
正因为**不返回分数/排名**，Agent 无法察觉近邻集合的抖动。同 query 两次必须返回同一集合，
tie-break 显式定死（按 `unit_no`）。分数隐藏这个产品选择，把"确定性"从实现性质变成了契约。

**I. 重建是一等语句，不是运维脚本**
F6 在 F5 之前落地，索引先于生产者存在。"从 `mem_recall_units` 全量重建 vec0"必须是一条
语句；否则"可重建"永远只是口头的（判据④）。

## F6 的拆法与顺序（2026-09-21 咨询）

**总判断**：F6 的真正内容不是"接上 vec0"，而是**先把向量字节在 `mem_recall_units` 上立成
真相、把库级身份锁立成独立事实**；vec0 是这两件事的派生物，最后接、且必须能被整张扔掉重建。
按这个顺序拆，vec0 的上游风险全被隔离在最后几步，前面都是纯 SQL、可验收、不依赖 cgo。

| # | 内容 | 依赖 vec0 |
|---|---|---|
| S0 ✓ | 构建 spike：绑定进构建 + `Auto()` 注册时机 + 启动断言 + 模块可用性断言（2026-09-21 完成） | 是（只此一步验证） |
| S1 | 库级 `(model, dims)` 身份锁 + 校验拒收 + `RECALL` 报"N 个单元未就绪" | 否 |
| S2 | 向量字节落 `mem_recall_units`（真相）+ 两个入口 + `content_hash` 重算校验 | 否 |
| S3 | 建 vec0 + 同事务增量插入／按 `unit_no` 删 | 是 |
| S4 ✓ | `REPAIR VECTOR INDEX IN DATABASE <db> LIMIT <n>`：把派生索引**修到与真相一致**（不是 drop 再建；DROP + REPAIR 就是全量重建），受 `max_affected_rows` 约束、重复到 `remaining` 为 0 | 是 |
| S5 ✓ | 向量召回接进 `RECALL`（`NEAREST :v` 子句）：就绪过滤、`k+m` 取回、我们这层按 `(distance, unit_no)` 定序、跨表归并；查询向量走 base64 小端 float32 契约 | 是 |
| S6 ✓ | 确定性／幂等验收套件：同 query 同集合（含**距离并列**时按 unit_no 定序）、重复接受同一向量不变、**重建后的索引逐字节等于增量维护的索引** | — |

**S0 与 S1 可并行**；S1 做完即有可验收产出且完全不依赖 vec0 编译成功。**S4 必须早于 S5**。

**S0 的实现形状（已落地）**：`sqlite_vec.Auto()` 用 **cgo 构建约束**（`//go:build cgo`）挂进
`internal/sqlstore`，配一个 `!cgo` 兜底文件——**不加新构建标签**，因为"能开库"本来就要求 cgo
（mattn 驱动也是 cgo），所以"每次打包都带"这件事不靠标签靠约束，没有会被忘记的开关。
`Open` 先注册（`Auto()` 是 auto-extension，必须在第一个连接之前跑）、再开连接、再断言
`vec_version()`；断言失败就**拒绝打开数据库**并说明原因。`CGO_ENABLED=0` 的 vet／lint stage
走兜底文件，两个 `GOOS` 都已实测通过。

**为什么 vendor 上游的 C，而不是依赖它的 Go 包**：上游那个包无条件 `#include "sqlite3.h"`，
于是"能不能编"取决于宿主机装没装 C 的 SQLite 开发包，而且它找到的头文件与我们所链的库
不是一回事——macOS 上碰巧拿到 SDK 的 **3.43.2** 头去编 **3.50.4** 的库（静默版本错配），
Linux 容器上直接没有这个头，构建死在 `fatal error: sqlite3.h`。所以把 `sqlite-vec.c/.h`
抄进 `internal/sqlstore/vecext`，再把驱动的 `sqlite3-binding.h` **生成**成包内的
`include/sqlite3.h`（与所链库**严格同版本**），用
`#cgo CFLAGS: -I${SRCDIR}/include -DSQLITE_CORE`。生成物由 `format` stage 重跑生成器并
`git diff --exit-code` 看住：驱动一升级、漏了重生成就当场红。代价是自己跟上游 sqlite-vec
的版本——它还在 0.1.x、我们只用 vec0，单文件 diff 可审。

**跨平台验证的补丁**：宿主门禁编不到 Linux 的 C（两个 `GOOS` 的 vet/lint 都跑
`CGO_ENABLED=0`，走的是兜底文件），所以补了 `scripts/ci-linux.sh`——在 Docker 里跑 Linux 的
cgo 构建，加上所有开真库的测试。**CI 只跑 macOS**（已定），所以 Linux 的 cgo 这一半只剩这个脚本能验——它是可选工具，
不进门禁；`scripts/ci.sh` 里对 Linux 的覆盖只有 `GOOS=linux` 的 vet/lint 编译检查。

### 已定的四个形状

1. **两个入口，都不是临时物**：写入语句的可选向量字段（最快路径），**加上**一条一等的
   "给已存在单元后填向量"语句。后者正是 F5 客户端排空要打的 API，所以 F5 = 队列 +
   CLI 自动算 + 排空，排空就是调它，零拆除。**F6 不造队列表**："拒收转队列"在 F6 实现成
   "单元保持未就绪 + 结构化拒收原因回给客户端"——未就绪是查询出来的视图，不是新存储。
2. **vec0 每 (库, 表) 一张**，`rowid = unit_no`。全局单表出局：`float[N]` 建表即固定，
   而 N 是**库级**锁，不同库不同 N，一张表放不下。每表一张还让 `IN <table>` 与权限 scope
   直接落成"选表"，不依赖 vec0 的 partition key／metadata 列过滤（那是 sqlite-vec 里最不稳的
   部分）。代价是跨表要多次 KNN 再归并——同库同模型同维度，距离可比，归并可行。
   **归并全序定死为 `(distance, table_id, unit_no)` 并写进不变量。**
   注：`unit_no` 是**全局单表内单调**（`mem_recall_units` 一张表装所有库所有表，
   `AUTOINCREMENT` 保证不复用），所以每库一张也不会撞 rowid；选每表一张是为了上一条的理由。
3. **先有锁，再建表**。锁必须能在 vec0 完全不存在时独立存在——"建表即锁"把真相塞进派生
   结构，`DROP` 掉 vec0 重建后锁就没了、重建语句立刻不幂等，而"索引可重建"是核心验收。
   顺序（同事务）：首次接受向量时，库无锁 → 写锁 + 建 `vec0(float[N])` + 插入；有锁 → 校验
   → 插入。锁落在普通元表一行上。
4. **重建放 `REPAIR` 系**：`REPAIR ... REBUILD VECTOR INDEX`，语义是"从真相重放派生物"，
   同一个面将来也能收 FTS5 的 rebuild。排在 S5 之前还白得一个 oracle——
   **增量维护的结果必须逐字节等于全量重建的结果**。最终验收：`DROP` 掉所有 vec0 →
   `REPAIR` → 同一组 query 返回完全相同的 route_id 集合**和顺序**。

### 两个风险

- **最大风险不是构建**：构建风险（两份 SQLite 符号、`Auto()` 注册时机）一天内能证伪，
  所以它是 S0 而不是风险。真正的风险是——**我们把确定性升格成了不变量，但 tie-break
  托付给了 v0.1.x 上游的未承诺行为**。它不会在 F6 炸，会在半年后升版本时炸。对策写进 S5：
  向 vec0 要 `k + m` 条，拿回 `(rowid, distance)`，**在我们这层**按 `(distance, unit_no)`
  重排取 k；若第 k 名与第 k+m 名距离相等则扩大 m 重取。vec0 只负责"距离算对"，**顺序归我们**。
- **影子表命名**：vec0 会自动建 `<表名>_chunks`／`_rowids`／`_vector_chunksNN`。本仓目前
  **零处**按 `mem_` 前缀枚举表（全仓无 `sqlite_master` 查询），所以沿用 `mem_recall_vec`
  与既有 `mem_recall_fts` 保持一致；真正的规则与名字无关——**任何将来按前缀枚举内部表的
  迁移或校验逻辑，必须排除虚拟表的影子表**，这条写进不变量。

### 顺序修正（2026-09-21 咨询后）

原计划把"锁 + 未就绪上报"（S1）排在"真相列 + 入口"（S2）之前，理由"不依赖 vec0 编译"。
**这个理由没有区分度，论证自己塌了**：向量字节只是 `mem_recall_units` 上的一个普通 BLOB 列，
vec0 才是派生物，真相列同样不依赖 vec0。真正的依赖链是——未就绪判据是一条 SQL 谓词，
它的每个操作数都在真相列上：

- **缺一列关键字段**：只有 `embedded_at` 时，"这条向量是对**哪段文本**做的"没有答案，
  拿 `embedded_at > updated_at` 当代理是**依赖时钟的假答案**。所以真相是**两**列：
  `embedding BLOB` + `embedded_content_hash TEXT`。
- **锁不能先落**：锁不是一张配置表，它是**接受判据的一半**——
  接受 = `(model, dims) == 库身份` **且** `写入时带的 hash == 单元当前 content_hash`。
  锁单独先落，落下来的是一行没人读的配置加一个算不出来的告警。

**修正后的切法**：

| 步 | 内容 | 依赖 vec0 |
|---|---|---|
| S1′ ✓ | 真相列（`embedding` + `embedded_content_hash`）+ 库身份锁 + 接受/拒收 | 否 |
| S2′ ✓ | 未就绪上报（`executor.Output.Warnings` 接 `result.Notice` + doctor 计数） | 否 |
| S3′ ✓ | vec0 索引，从真相列派生，`rowid = unit_no`，可重建可丢弃 | 是 |

**锁的粒度 = 召回的作用域 = Memora Database**（不是实例级）：vec0 每 (库,表) 一张、
`float[N]` 建表即固定，维度本来就绑在比实例更细的粒度上，实例级只禁止合法差异；而一次
RECALL 跨表返回，表级锁会让同一次召回混入不可比的向量空间——不返回分数，但**排序**仍跨
空间发生，静默污染换个地方复发。库级要接的代价是一条结构性规矩：**任何碰 embedding 的
查询必须走 `database_id`**（就绪谓词写成固定 join：unit → 库身份行）。

**锁存在 `mem_databases` 的列上**（`embedding_model` / `embedding_dimensions` /
`embedding_locked_at`），**不放 `mem_config`**：库身份不是可调项，而 `mem_config` 是带
revision 的可改通道，把不可改的东西放进可改的通道迟早被改。时机 TOFU——第一条被接受的
向量定身份，此后不可原地改，改 = 显式清空该库向量重嵌。

**未就绪是派生的，不建队列表**：谓词 = 没有向量 ∨ 向量算的不是当前文本 ∨ 向量不属库身份。
于是"拒收转队列"里的"队列"就是**未就绪单元这个视图本身**——不新增存储、不会忘记更新、
也没有"该二进制永远排不掉的积压"这个问题（排不掉就等于一直未就绪，而它看得见）。

### S3′ 落地后的两条注意（给 S5／S4）

- **索引里允许有陈旧行**：文本变了但向量没重算时，索引行**故意留着**（陈旧的向量是已知状态，
  由 `embedded_content_hash <> content_hash` 判出来）。所以 **S5 的向量召回必须 join 就绪谓词**，
  否则陈旧向量会把召回指到一条它已不描述的路径上。这也正是"就绪是派生的"这条设计的用武之地。
- **表级索引的生命周期**：索引按 (Database, Table) 惰性创建（第一次接受向量时，因为 `float[N]`
  建表即固定，此前没有已提交的维度可声明）。目前**没有**在表被删除时丢掉索引文件的对象；
  这是 S4 的活儿——重建路径要能枚举既有索引，`mem_recall_vec_indexes` 就是那个枚举来源
  （用注册表而不是按名字前缀扫 `sqlite_master`：前缀会连虚拟表的影子表一起匹配到）。

### S5 定下的两条（2026-09-21）

- **查询向量的线上形式是契约**：`base64.RawURLEncoding` 的小端 float32 紧凑排列，长度 4 的
  倍数、不得含 NaN／Inf、维度须等于库锁定维度。理由是**解错端序解出来是合法向量**——
  返回一批合法但错的路径，而召回不返回分数、答案里看不见。MSQL 没有数组类型，数字数组
  还会把 `[]any` 变成一等参数值，牵连整个求值器。
- **`LIMIT` 是输出截断，不是召回强度**：两路内部候选数（向量路的 `k+m`）是实现细节；
  并集去重后按"表名 + 路径"字典序截断到 `n`。这样单臂与并集里 `LIMIT` 含义一致，且不需要
  分数或权重——那会与 ADR-0012「向量只用于定位，从不产出事实」冲突。
  `MATCH :q NEAREST :v` 的语法现在就定死（MATCH 在前），执行期在 F7 前返回
  `unsupported_statement`，而不是只用一路作答。

### 提交入口的落地（2026-09-21）

**后填入口先做，而且它是 F5 排空要打的那个 API**：`ACCEPT VECTOR :v FOR UNIT :unit
IN DATABASE <db> MODEL :model HASH :hash`。一条语句一个嵌入——语言没有数组类型，所以
批量＝一批语句，客户端可以在一次请求里发多条（需要时外面套 `BEGIN`/`COMMIT`）。

`HASH` 是宿主**嵌入的那段文本**的哈希，引擎按自己的载荷规则重算、不匹配即拒：这样
"客户端要复刻引擎的载荷规则"这件事从**静默漂移**变成**被检查的握手**——规则漂移的
结果是"没贴上"（可见、可补），而不是"贴错了"（不可见、不可修）。

**写入语句的可选向量字段仍未做**：它只是让同一次写入顺手带上向量，是快路径而非必需
路径（后填入口已经覆盖全部功能）。它落地时复用同一份编码与同一条握手。

### S6 的三条不变量（2026-09-21）

1. **同 query 两次必须同一集合与同一顺序**——包括距离并列时谁活过 `limit`。这正是上游
   排序承诺覆盖不到的地方（sqlite-vec 对等距的次序不是承诺），所以要有一条测试钉住：
   三个单元同向量、`limit=1`，五次都返回同一个、且是最小 `unit_no` 的那个。
2. **重复接受同一向量不改变任何东西**——单元只有一份真相、索引只有一行；客户端没收到
   第一次应答而重试，不会双写。
3. **重建后的索引逐字节等于增量维护的索引**（含被故意保留的陈旧行）。这比"同一组查询
   返回相同结果"更强：它不经过查询的排序，直接比对 `(rowid, embedding)` 字节。
