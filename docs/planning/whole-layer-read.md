# 整层读取：读取端不设宽度上限，界只有时间阀

状态：**实现计划**（未开工，等开工）。前置实测见 `docs/decisions.md`。

## 为什么读取端不该有宽度上限

一层的大小由**写路径**约束：`route_policy.branch_fanout`（默认 12，一次最多 +4，上限 100）的含义是
"一个 root/branch 最多挂几个活孩子"，在 `createNode`（每次新建 Route）与 ROUTE MUTATION 计划
（重新挂载）两处都拒。读取端的 `router.CompleteNodes` 注释写的就是这件事：

> A route layer is bounded by the Database's `route_policy.branch_fanout`, **not by a read-side
> budget**, so there is nothing to page — and a listing that somehow did not fit is an error rather
> than a page.

所以 `jev_tree.py` 里的 `MAX_FRONTIER = 4` 是**读取端自己发明的一个上限**，与系统设计矛盾：它把写路径
已经保证合法的一层，按到达顺序砍掉一部分。正确的读取语义是——**当前层有多少个节点就读多少个，整层交给
jev 判**（`choose_layer` 本来就是这样），没有宽度上限。

## 为什么界只该是时间阀

`MAX_JEV_CALLS = 12` 与 `MAX_DEPTH = 5` 限的是**树的属性**，而树的形状已经由写路径逐层约束、且是有限
的（`empty` 还会剪枝）：走完自然停。拿一个常数去限它，等于在读取端猜写路径的形状，猜错就是静默错答。

实测（真库、真 provider、只读）：

| 场景 | 决策 | provider 时间 | 墙钟 | 真落点 | 走完了吗 |
|---|---|---|---|---|---|
| 最宽的意图（2 库 / 2 表 / 62 个 route 节点） | **13** | 5.36 s | 6.22 s | 35 | 走完整棵树 |
| 窄意图（"我有哪几段实习"） | 3 | 1.37 s | 1.58 s | 2 | 走完 |
| 同一宽意图，保留 `MAX_JEV_CALLS = 12` | 12 | 4.43 s | 5.22 s | 31 | **差一次调用没走完，恰好砍掉一个分支** |

**12 这个数比"把这棵个人库整棵走完"还少一次。**

时间阀限的是另一件事：**hosted provider 的不确定性**（挂死、重试、网络黑洞）——那不是树的属性，是外部
依赖的属性，读取端有责任兜。保留一个，值给到明显高于最坏正常路径的量级（现在最坏 6.2 s → 取 120 s），
它只应该在"不正常"时响。

**放弃的是"单次检索成本可预测上界"**：删掉调用数上限后，计费次数由树规模决定，库长大到几百上千节点时
宽意图会变慢变贵。那时该动的是**写路径**（收敛树形、提高剪枝率），或者让**调用方按场景传预算**——而不是
在读取端埋一个默认常数替所有人做决定。这条留作入口，等真的痛了再加。

## 修法（一个 Feature，一个分支）

1. **删掉读取端的宽度上限**（`MAX_FRONTIER` 及其"按到达顺序保留前 N 个"的截断）。
2. **删掉 `MAX_JEV_CALLS` 与 `MAX_DEPTH`**：树有限，走完自停。
3. **只留一个时间阀**，值按"明显高于最坏正常路径"取（120 s 量级）。
4. **没走完的分支不许写进 `landings`**：任何停住（时间阀）一律进单独的"停在这里"字段（带原因与
   已走/未走计数），并令 `incomplete: true`。现在它们混在 `landings` 里、只靠 `termination` 区分
   ——这正是"够不到答案"长得像"搜过、没有"的来源。
5. **环**：写路径已经负责（`routemutationplan` 的 descendant 检查 + "Router subtree contains a cycle"，
   而 `createNode` 只能挂在既有父节点下、造不出环）。读取端**不再用深度上限假装防环**，改为带一个
   `visited` 集合：撞到重复就跳过，并记一条**数据损坏告警**——那是 doctor 的领域，不是"走得太深"。
6. **Skill 文案**：`incomplete` 与"停在这里"写清怎么读；`incomplete` 时的正确动作是**收窄**
   （显式 `table=`，或把要求拆成一个主题）——那减少的是待走的分支数。

## 判据

- RED：两库两表那个可复现用例，断言 `modules` 的根分支不被丢、目标行落地。
- 断言 `landings` 里**不含**任何未展开的节点；停住的分支出现在"停在这里"字段且 `incomplete: true`。
- 断言最宽意图在真库规模上能走完整棵树（决策数等于该库的层数，而不是撞上某个常数）。

## 坑

- 去掉宽度上限后落点会变多（实测缺口那问 35 个真落点）：**召回换来了噪声**，这是有意的——jev 判不
  出来时宁可整层给出来，也不按顺序赌。Skill 要教调用方怎么用这个结果。
- `incomplete` 是新的读法：模型看到 `incomplete` 却当完整答案用，是这一块最容易出的错。
- **别再引入第二个宽度或次数上限**（哪怕换个名字）；界只许有时间阀这一种。
