# jev 分流阶梯：什么时候走树、什么时候用 jev、剩下的活怎么排

状态：**实现计划**（未开工，等开工）。契约细节见 `docs/planning/whole-layer-read.md`；
标签质量见 `docs/planning/route-purpose-contract.md`（已上线）。

## 分流阶梯：判据在输入形状上，不用"试了再说"

1. **输入含专有字面量**（公司名、人名、项目名）→ 直接关键词 `RECALL`，命中就回表，**根本不进树**。
2. **输入是模糊近义**（"类似的""那种感觉"）→ `RECALL … NEAREST`，同样只为拿位置。
3. **输入是类目型**（"我有哪几段 X""关于 X 的缺口/决定"）→ 走树，这是树的本命。**默认执行器是
   agent 自己**：一次请求可以带多条 `SHOW ROUTES`，所以一层（或下一层的全部兄弟）只花一轮，
   而 jev 走树要为**每个分支节点**付一次 hosted 判定。**这一条是 2026-09-23 反转的**，依据见下。
4. **宽意图不预先分流**：从 Database 层起跑**一次** jev，靠 `empty` 剪枝自己收敛。
   "第一层就散成多库多表"恰恰是 jev 最稳赢"agent 自己逐层走"的场合。
5. **不把 jev 改成打分选 top-k**：`set`（"答案在不在这里"）是对的形状。实测 9 个候选并成一个请求
   无判别力（.47–.66、地板 .37），那条边界就是这条规矩的证据。

> **反转（2026-09-23 实测）**：本文件原先写"**jev 是树的默认执行器**"。实测推翻了它——同一批三问、
> 从第一次检索动作到事实到手：**agent 自己走 16.27 s / 5 次调用 / 工具时间 0.15 s**；
> **jev 走树 32.74 s / 6 次调用 / 11.7 s 等 provider**。原因是**成本模型不匹配**：agent 的花费按
> **广度轮数 ≈ 树深**计（这棵树深度 2–3 → 4–5 轮），jev 按**分支节点数**计（62 节点里有 13 个分支层 →
> 13 次判定）。**"浅而宽"正好是 jev 最吃亏的形状**；深度 ≥5 时它的成本模型才顺风。
> 所以：默认 = agent 自己走语义索引（批量 `SHOW ROUTES` + 回表读）；**jev 挂在两个可数信号上**——
> 单层宽于约 40 行，或已过第 5 层仍未到叶子；再加一条"需要可重放的逐层判定记录"。
> **不成立且不再写进理由的**：①"大库省上下文" —— 纯机制论证、**没有 token 数字**（要量的是同一批
> 问题下 agent 自走塞进上下文的层清单总 token vs jev 路径的）；② 窗口 2× 的差距里有多少是抽样噪声
> 分不开（自己走那一臂跨三轮是 44.9/39.3/67.6 s），**结论应靠调用次数（5 vs 6）与工具时间（0.15 s vs
> 11.7 s）这两个低方差量**；③"4/5 vs 5/5 目标行"不能当 jev 的准确率优势（单次采样差一行，而同一段
> 里 jev 有 4 次跑 4/8 的宽层错判）。
>
> **不再投入的方向**：优化 jev 的速度（~12 s 里 11.7 s 是 provider 往返）、让它在浅宽树上赢、
> 以及"让 agent 批量调 jev"（一次一判定是它的接口形状）。

> **更正**：`docs/decisions.md` 里"宽意图是负收益、不该走 jev"那条结论**被推翻**——它依据的 65.1 s
> 来自带读取端上限的旧版（漏答案、agent 手工补）。修掉上限后，同一宽意图整棵树的**脚本**时间是
> 6.22 s 并命中两行。**但"修好之后的 agent 级总时长"还没实测**，那是这一块的验收项（见下）。

## 剩下的话，按这个顺序

1. **先补 `ALTER ROUTE … SET PURPOSE`，再回填 44 条**——**前置，不是收尾**。标签质量是 jev 准确率的
   天花板：实测同层里只要有一条真描述，切分就干净（.10 对 .88、地板 .06）；全是复读时它只能
   `undecided`。**但这一步卡在一个引擎缺口上**：`purpose` 建完之后**没有任何语句能改**
   （`memora parse "ALTER ROUTE :route SET PURPOSE :purpose"` 直接拒，`ALTER ROUTE` 只有
   `SET SYNOPSIS` / `SET ALIASES`）——于是引擎**拒了新的、修不了旧的**，真库上那 44 条根本无法修复。
   所以顺序是：**先加 SET PURPOSE（与 `CREATE ROUTE` 同一条判定），再回填**。
1b. **aliases 要先有人读，才值得填**：查证发现 route 的 `aliases` 现在是**只写不读**——召回单元取的是
   行的 `title`+`summary`（ADR-0008），走树只喂 `name`+`purpose`，安全与目录匹配用的是
   **Database/Table** 的 aliases。所以"给每个节点补主人会用的词"这件事，前提是**走树把 aliases 也喂给
   jev**（短词、不是长文，与"别喂 synopsis"那条不冲突）。否则回填 aliases 对检索零效果。
2. **让 `SHOW ROUTES` 的叶子顺手带出 `row_id`**——一处改动两路受益：jev 那 35 条 `OPEN ROUTE` 归零，
   **自己逐层走的模型也省**（列表里就有行号，不必再开叶子）。收益最大、风险最低。
3. **`whole-layer-read.md` 那一包**：删读取端宽度/次数/深度三个上限、只留时间阀；没走完的分支不进
   `landings`；`visited` 防环 + 数据损坏告警；落点带 `database`/`table`；Skill 写清"定位 vs 回表"。
4. **落点按 `(database, table)` 聚合 + 带列名**：等第 2 步落地后，这基本是纯格式化——35 个落点真实是
   6 张表上的 6 组 row_id；顺手带上列名，省掉 agent 写回表 SQL 前
   还要 `DESCRIBE` 一轮。
5. **不做**：jev 的缓存、并发、小模型降级、阈值调参——1.4 s 与 6.2 s 都不是瓶颈，现在做是提前优化。

## 坑（进契约或进实现）

- **`empty` 现在是静默的**：判错一次，整条分支无痕消失，契约里只有"停在这里"、没有"我剪掉了什么"。
  必须给剪枝留一条**可审计记录**，否则漏答永远无法归因，只能靠人肉发现（旧版那次就是这样被发现的）。
- **报进 `undescribed_at` 的层必须强制按 `undecided` 整层展开**，不许采信 jev 在这一层的判断——
  否则那是拿 name 当 purpose 在判，坏标签会**直接变成漏答**。这是第一块的一个后续小改。
- **无上限 + 按量计费**：时间阀只兜 provider 挂死，兜不住"13 次决策变 130 次"的账单。要的是决策次数的
  **观测与告警**，不是再塞一个上限。
- **上线"落点只有叶子"之前先扫存量**有没有非叶子承载事实（真库现在 `orphan_rows`/`multi_leaf_rows`/
  `mismatched_mounts` 都是 0，干净；但这条要进判据）。
- **验收项**：修好之后要再做一次**不带上下文的 agent A/B**（同一组跨库三问），用真实总时长回答
  "jev 到底快不快"——脚本层的 6.22 s 不等于 agent 层的结果。
