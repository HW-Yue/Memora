# 中文与短词的召回：为什么「实习经历」搜不到

状态：**诊断已定，方案待开工**（2026-09-21）。用户在 Admin 搜索页实测发现的问题。

## 实测（`me` 库，关键词臂）

| 查询 | 结果 |
|---|---|
| `oppo` | 命中 4 条（正文里有 "OPPO"） |
| `实习` / `经历` / `后端` | **被拒绝**：`RECALL needs at least 3 characters` |
| `实习经历` | **空** |
| `实习 经历` | **空** |
| `实习经历`（向量臂） | 命中：`实习/OPPO`、`实习/悠悠有品` 等 |

## 病因（两层，都不是"没做切分"这么简单）

1. **索引是 trigram（连续子串）**：FTS5 的 trigram 分词器把正文切成 3 字滑窗，所以
   - **1–2 个字符的查询永远匹配不到任何东西**——这就是那条"至少 3 个字符"的拒绝存在的原因：
     空结果读起来就是"没找到"，宁可拒绝；
   - 更长的查询被当成**一整段连续子串**：`实习经历` 要求正文里真的连着出现这四个字，而没有任何
     正文（每行只索引 `title` + `summary`）是这样的——语义树节点叫 `实习`、表描述写
     "实习与工作经历"，**树节点名与表描述都不在被索引的正文里**。
2. **查询端不切分**：中文没有空格，`实习经历` 就是一个词，引擎不会把它拆成 `实习` + `经历`。

用户猜的两条里，**"向量没做好"其实是他跑着的 Admin 是旧 bundle**（前端编在二进制里，没接上
向量支路），重启后同一个问句走向量臂是能答的；**"没做切分"是真的**。

## 顾问的结论（2026-09-21）

- **只降阈值 + 短词走扫描，修不好他举的那个 bug**：`实习经历` 是 4 个字符、每个词都 ≥3，
  按"最短词选路径"的规则仍然走倒排，仍然返回空。
- 真正的病因是两条：**索引面太窄**（树节点名、表描述不进正文）+ **中文没切分**。
- 最大风险：**修法与病因错配**，制造"已修复"的假象。
- 次生风险：`LIKE` 扫描没有相关性信号、只能按 `unit_no` 排序，喂给 RRF 相当于**注入一条伪排名臂**，
  会稀释向量臂的真信号。

## 实测：病因在索引侧，不在排名（临时 SQLite，未碰实例）

同一句话，一次连着写、一次把词用空格隔开：

| tokenizer | `实习`(2) | `经历`(2) | `后端开发`(4 连续) | `后端开发实习`(6) |
|---|---|---|---|---|
| trigram | MATCH **0** / LIKE 2 | MATCH **0** / LIKE 1 | MATCH 1 | MATCH 1 |
| unicode61 | MATCH 1（只有被空格隔开的那条） | MATCH 1 | MATCH **0** | MATCH **0** |

`bm25()` 是**排名函数**：真实命中时正常排序，`MATCH` 为 0 时没有东西可排（两条都实测过）。
所以"bm25 应该能查两字词"是把 analyzer 与 similarity 混在一起——ES 里同样要靠 `ik`/`jieba`
或 `ngram(min_gram:2)`，换 similarity 无用。

## 方案（bigram 索引；顾问 2026-09-21 认可，取代上一版的 LIKE 扫描）

1. **把 trigram 索引换成 bigram 索引**：为每个单元的载荷生成全部 **2 字滑窗**作为 token
   （unicode61 分词即可），写进派生 FTS。两字词就是一个 token，天然可索引。
2. **查询端也切成 bigram 并 `AND`**：`实习经历` → `实习 习经 经历`（空格＝隐式 AND）。
   四字以上要求所有 bigram 同时出现，近似强制连续。**写端与读端必须共用同一个切分函数**，
   否则静默零召回。
3. **≥3 字的查询加一道连续性校验**：命中后用 `instr()` / `LIKE '%原串%'` 做**后置过滤**
   （不是召回臂，只是精排信号），把"所有 bigram 都在、但顺序/位置不对"的假阳性压掉——
   这是顾问指出的最大风险（`北京上海` vs `上海北京` 这类重排干扰，加上高频 bigram 上 bm25 的
   IDF 区分度低）。
4. **最低长度 3 → 2**（用户要求）；1 个字符仍然拒绝——它连一个 bigram 都凑不出。
5. **trigram 不留**：两套索引＝双份膨胀 + 两条分叉逻辑，而 trigram 能覆盖的（≥3 字连续）被
   bigram + 后置过滤全覆盖。留着只会让"该查哪张表"变成新的 bug 源。
6. **迁移**：FTS 是派生层——drop 旧虚拟表、建新表、重建索引；真相与向量都不动
   （载荷不变，`content_hash` 不变，向量不重嵌）。
7. **Admin**：搜索框最低 2 个字符。

### 为什么不用"短词走有界 LIKE 扫描"（上一版方案）

顾问指出：扫描**没有相关性信号**，喂给 RRF 相当于注入一条**伪排名臂**，会稀释向量臂的真信号。
bigram 方案让任何 ≥2 字的查询都**走索引、有 bm25 真实排名**，扫描、无序臂、以及为此新增的融合
分支全都不需要。

## 为什么不用 jieba（顾问 2026-09-21 结论）

**结论：现在用 bigram，词典分词留作日后可替换的切分实现。**

- 这个语料正是词典最吃亏的地方：**个人库 + 大量 OOV 专有/自造词**（`悠悠有品`/`CoHabitat`/
  `DSH`/`原醛`）。jieba 对未登录词只能靠 HMM 猜或扩词典，而这些恰恰是最需要查准的词；
  **bigram 对专名零漏召**。
- 规模站在 bigram 这边：几千行的倒排表，bigram 那点 token 膨胀无关痛痒；`instr()` 连续性
  后置过滤跑在几十条候选上等于免费，过滤后的 bm25 是**真排名**，RRF 契约完整满足。
  ASCII 词仍按 unicode61 的规则切，不受 bigram 影响。
- 共同约束那条更关键：切分读写共用、**词典版本一升就要全量重建索引**。bigram 的切分是纯函数、
  零版本、零依赖，确定性可以直接被测试钉死；词典方案把检索质量绑上一个**会漂移的数据文件**，
  OOV 一出现就要扩词典再重建——没必要把重建触发器从"代码变更"扩大到"数据变更"。

**弃选**：`gojieba`（cgo）——为它引入 C++ 工具链，与"3 个直接依赖、一条命令编双架构"的发行路径
不值当；`jiebago`/`sego`（纯 Go）可行，但词典进仓库是几 MB 膨胀，换来的只是中文散文那一层的
切分优雅——而散文恰恰是**向量臂已经覆盖**的部分。

**什么时候再换**（切换判据，写死在这里）：bigram 的精度真正成为瓶颈时——正文上万行、误召可测量。
切分函数集中在一处，"bigram → 词典分词 + 重建一次索引"的替换成本本来就低。

## 验收

- 上面那张实测表的四组全部固化成**回归用例**，重建索引后逐条跑：
  `实习`(2) / `经历`(2) / `后端开发`(4 连续) / `实习经历`(4 不连续) 都能命中该命中的行；
- `实习经历` 的假阳性被后置过滤压住：只含 `实习` 与 `经历` 但不相邻的文档**不得**因它命中；
- `oppo` 的命中集合与顺序不退化；两臂 RRF 融合顺序不变（没有无序臂这回事了）；
- 迁移后 `doctor` 全 0、关键词召回与向量召回都正常；
- 重启 Admin 后页面上重测同样四条（排除旧 bundle 干扰）。
