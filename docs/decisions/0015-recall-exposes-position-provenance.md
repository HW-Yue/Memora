# ADR-0015：召回可以说出"哪条臂找到了这个位置"，但不给强弱

状态：Accepted，2026-09-22。修订 [ADR-0013](./0013-recall-fusion-by-rank.md) 第 5、6 条的字段清单：
**位置出处可外露；分数、距离、名次、相关性解释仍然不可。**

## 背景

ADR-0013 把两路召回按名次融合（RRF, k=60），响应只有位置：每段 `name` + `route_id`，末端
`kind` / `object_id`。结果是**两条臂都命中的位置与只有一条臂命中的位置在响应里完全一样**。

这在一个真机上变成了用户可见的错：Admin 搜索页对两字查询「实习」列出 10 个位置，其中两个是
完全无关的短记录。核查（实测）：该 Database 的关键词臂只命中 1 个位置，那两个**纯粹来自向量臂**；
把库里 44 个单元全部按余弦排序，真正相关的在 0.34–0.37，那两条是 0.279 / 0.278，中间还夹着无关
记录——两字中文词的 embedding 区分度本来就低，而引擎没有阈值、也不返回分数，于是向量臂的尾巴
混在列表里，看起来和别的命中一样。页面当时把"这一库跑了两条臂"这个**库级**事实盖在**每张卡**上
（`receipt.vector.ran ? "两臂融合（RRF）" : "关键词"`），把"仅向量"的弱尾巴读成了两臂都认可的命中。

## 决定

1. **`RECALL` 的每个命中多一列 `arms`**：找到该位置的臂名列表，固定顺序，取值
   `["keyword","vector"]` / `["keyword"]` / `["vector"]`。单臂语句（只 `MATCH` 或只 `NEAREST`）
   相应地只有一项。
2. **它是出处，不是强度、不是背书**：不带量纲、不随语料变化、也无法反推 RRF 分数（知道哪一项
   非零 ≠ 知道名次）。**两条臂都命中 ≠ 更相关**；任何调用方**不得**据此排序、过滤、设阈值，
   也不得把它渲染成强弱（Admin 的徽章是中性措辞，没有强弱视觉差）。
3. **顺序、`LIMIT`、`truncated`、平分回落到"表名 + 路径"的确定性一律不变**，都不读 `arms`。
4. **仍然不返回**：分数、距离、名次、权重、`matched_fields` 之类的内容级解释，以及任何免于回表
   就能当答案用的正文。`arms` 说的是**一次查询里哪条路定位到了它**，不是"为什么这条更相关"。

## 理由

ADR-0013 第 5 条禁的"原因"，指的是**相关性解释**（"因为匹配了这些词 / 因为语义接近"）——那是对
内容的事实主张，正是"向量只定位、不产出事实"要挡的东西。臂名不解释内容，它交代的是检索器自己的
机械路径，方向上反而**加固**那条产品规则：它让"这条只是向量定位出来的"变得可见，而不是让向量
冒充证据。反过来，没有它，调用方唯一能拿到的粒度是库级的，于是"库跑了两条臂"必然被读成"每条
命中都过了两臂"。

## 后果

- 引擎：融合时给每个位置累计臂名（`internal/msql/executor/archive.go`），单臂路径按臂名直接标注。
- Admin 搜索页：徽章改成逐位置的中性出处（`关键词+向量` / `仅关键词` / `仅向量`），库级事实回到
  说明行；页面新增一句"徽章是出处、不是强弱"。
- Skill：召回参考写明 `arms` 的含义，以及**`["vector"]` 是短查询里要警惕的一类**，看到它要回表
  读正文再判断。
- 契约面：`RECALL` 的列从 5 列变 6 列；消费方必须容忍新列（这与 `SELECT` 的 `route_paths` 随行
  字段是同一类附加）。

## 风险

**把出处读成背书**：`["keyword","vector"]` 看起来很诱人，会被下游当成"更可信"来排序或高亮。
本 ADR 第 2 条就是为堵这条：要改它得再开一条 ADR，并承担 ADR-0013 第 6 条列出的代价
（分数一旦进契约，模型与下游就会按它判断、按它截断、按它解释"为什么这条更相关"）。
